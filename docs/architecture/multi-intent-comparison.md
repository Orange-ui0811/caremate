# 多诉求改造：架构与对照实验

## 当前架构

根图新增task_precheck。开关关闭继续原单意图路径；开启后，安全提醒先行，再由结构化LLM提取完整任务列表，每项独立携带订单及原文证据，校验后进入串行任务图。纯知识/其他单事项回原路径。当前为V2；V1曾使用固定退款+投诉规则，真实评测已暴露漏项与串用订单问题。

新任务图依次：持久化安全提醒 → 完整任务计划与原文绑定校验 → scheduler → 订单/物流只读查询、退款审核预览、投诉响应或独立知识检索 → scheduler → 统一等待独立工单确认 → 本地事务写入与回执 → scheduler → 汇总。选单前独立保存等待状态，恢复后复验订单归属，已完成事项不重跑。

SQLite保存执行控制状态，MySQL保存计划历史、助手消息、可回放事件和幂等回执。SSE先发送已提交提醒、再发送持久化完成的中断卡；客户端按消息ID去重，重开会话恢复未办卡片。普通单意图仍由LangGraph确定性步骤和单主Agent工具环共同处理。

新退款任务只提交人工审核请求，不判断最终退款资格；原退款Agent路径可能提供政策解释或引导其他操作。对照时必须检查同一业务断言的依据，不能只按有没有调用Agent判断优劣。详见 `multi-intent-workflow.md`。

## 已执行的真实多意图业务实验

第一轮 `data/multi-intent-eval/20261103/REPORT.md`：原单意图实现与V1固定规则工作流，真实模型、真实检索，固定30个场景及62项业务要求。整场景成功15/30→19/30，但三诉求组1/6→0/6，错对象退款工单2→5，说明恢复结构改善没有解决完整任务识别和参数绑定。

第二轮 `data/multi-intent-eval/20261103-v2/REPORT.md`：复用V1已保存的30条轨迹，V2按相同题目、知识快照、动作策略重新调用，逐题输出与SQL回执全部保留。新旧调用时间不同，每组只有一次结果；不是同步随机实验，也不是独立盲测。最新数字、失败诊断及冻结后新订单号探针以该报告为准。

两轮主指标均为事项有效回应、事项终态及整场景成功，不用提醒时序代替多意图能力。订单与物流使用两版本共用夹具，工单只写隔离数据库；真实调用DeepSeek-V4-Flash、BGE-M3和BGE-Reranker，不能表述为生产订单系统验收。模型裁判之外增加正确工具调用、可见业务事实和工单SQL回执检查；内部task_plan不作为成功标签。

## 早期结构测试：仅提醒时序

脚本：`python -m pytest tests/graph/test_multitask_comparison.py -q`。

使用20个预先写入CASES的构造问法：10个需要及时提醒，10个否定/假设/转述控制。每题三组，共60条初始执行轨迹，真实测试MySQL和SQLite checkpoint。每题独立清理workflow记录，每组使用不同会话、不同checkpoint文件，轮换执行顺序。

| 组别 | 图与SSE适配器 | 目的 |
| --- | --- | --- |
| A_before | 实现前备份中的build.py与runtime.py | 旧结构基线 |
| B_new_disabled | 当前代码，MULTI_INTENT_ENABLED=false | 控制公共基础设施修复的影响 |
| C_new_enabled | 当前代码，MULTI_INTENT_ENABLED=true | 新任务入口的效果 |

各组共享的nodes.py已逐字节校验与备份一致。指代消解固定透传、主意图固定为退款，不调用真实模型；因此仅能测结构与当前规则的提醒时序，不能测意图分类精度、最终业务完成率、答案质量或真实接口延迟。数据是围绕已知边界构造的开发集，不是盲测。

结果与问法保存于`data/issues/implementation-20261103/comparison/{cases,results}.json`。测试通过表示执行与记录正常，不表示每个问法都被正确识别；漏判与误报明确保留在结果中。

## 更大独立验收集：尚未执行

冻结新旧源码、知识库、订单夹具、模型及提示词、数据和运行配置；按语义族拆分开发集与独立测试集，阈值及规则只在开发集修改。原300题主要评估RAG，不替代多轮任务与中断评估。

新增固定100个场景，六类：明确复合诉求20、口语/隐含复合诉求20、否定/引用/假设20、选单/取消/新消息打断15、断线/重启/重复确认15、普通单意图回归10。预先标注所需事项、提醒必要性、订单归属、必须确认的操作、允许写入数与最终业务结果。

每场景复用相同用户轨迹：首问 → 选择指定订单或取消 → 分别确认/取消退款审核和投诉 → 必要时重连。旧版没有对应卡片时记录能力缺失，不伪造恢复参数；评价以外部可见事件、历史与业务回执为准，不要求旧版拥有新task_plan字段。

| 指标 | 计算方式 |
| --- | --- |
| 中断前安全提醒率 | 需提醒场景中，首个业务中断前已持久化且输出提醒的比例 |
| 不必要安全提醒率 | 无需当前风险提醒的控制场景中，仍输出紧急提醒的比例 |
| 事项覆盖率 | 有正确响应或明确说明处理状态的必需事项 / 必需事项总数 |
| 整场景成功率 | 所有必需事项、授权约束和期望状态均满足的场景比例 |
| 中断续办成功率 | 有效恢复后继续到正确下一事项的场景比例 |
| 未授权写入数 | 没有对应确认/订单归属时产生的业务写入数，目标0 |
| 重复写入/重复展示率 | 一次操作生成多笔业务记录，或同一事件呈现多次的比例 |
| 操作回执准确率 | 对提交成功/未执行/取消的表述与SQL回执一致的比例 |
| 延迟与成本 | 提醒首事件耗时、各次服务端处理耗时、真实调用数与Token；排除人为等待时间 |

故障位置至少覆盖：提醒入库后发送前、发送后ACK前、选单中断卡发出后重启、写入成功而checkpoint未推进、写入成功而HTTP回执丢失、并发双击、旧卡对新中断、跨用户/错误订单、后台依赖故障。

固定夹具结构回归与30题真实接口开发评测均已运行；以上100场景及完整故障矩阵尚未执行。后续需按语义族划分独立测试集，交替组别顺序、记录网络错误与重试，禁止事后挑最好一轮。不得用一次固定材料UI验收、开发集分数或回归测试通过数替代泛化效果。
