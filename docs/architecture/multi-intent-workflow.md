# Issue #3：完整任务计划与状态化多诉求工作流

2026-11-03 第二版本地实现，对应 [Issue #3](https://github.com/Orange-ui0811/caremate/issues/3)。环境默认仍为单意图；2026-11-04已增加本地客服页面的多意图开关，可按新会话选择两条路径。第一版只覆盖固定退款/投诉组合，实测遗漏第三事项、口语诉求，并把物流订单借给退款。第二版将任务识别和参数绑定一并重做，保留串行调度、独立确认和本地工单幂等，不能视为 Issue 全部验收完成。

## 执行与业务含义

新图在原意图路由前执行 `task_precheck`。关闭开关时继续旧图。开启后，规则只负责独立风险检查，风险提醒在任务规划模型调用之前落 MySQL，再作为 task_event 经 SSE 输出。随后 `app/core/task_planner.py` 使用结构化模型一次提取全部任务，而不是主意图或固定两种关键词。任务支持退款、投诉、订单查询、物流查询、知识问答及显式未支持事项；纯知识/其他单事项回原图处理。

每项包含 `kind/query/source/order_id/order_reference`：source须校验为当前用户原文跨度，V3.1允许受限的标点/空白对齐以及可验证的显式并列投影复原；order_reference仅在能回到原文时辅助消歧。订单绑定必须包含唯一对应编号和任务语义证据，退款不能借用物流片段的编号。证据不充分的订单置空并要求选单；否定任务不规划，也校验模型是否截短原文而恢复禁止动作。计划结构解析失败时明确说明未办理业务，避免只执行可识别的部分后假装全部完成。模型仍可能漏项或给出过短绑定片段，原文检查不等于语义正确性证明。

### V3订单绑定与澄清

120场景三轮记录中，V2有88次实际进入的多余选单：73次因引用过短丢失本来明确的绑定，9次未处理“这笔订单”的同消息指代，6次将显式并列退款号码清空。旧关闭模式的7次不能直接作为绑定精度基线，因为旧路径漏办更多事项；V3直接与已开启多任务的V2比较。

`app/core/order_binding.py`把原文按任务小句和明确连接词划分。绑定依据来自完整任务原文及其相邻主语，不再要求短引用本身必须同时出现动作词。明确“这笔订单”可承接同消息上一小句的唯一订单；“订单甲和乙都退款”展开为两个独立目标，再按类型和订单去重。模型改写的query或全句唯一数字不作为绑定证据，积分、金额、电话、日期和其他任务中的数字不能借作订单。否定、引述、假设等边界仍需检查，超过单轮任务容量失败说明而不截断。

已绑定且属于当前用户的订单直接验证和办理，不进入等待选单状态；缺参、歧义或非本人订单继续选单。选单卡说明业务目的，用户选择结果按当前任务保存，不给其他缺参任务自动共享；退款提交与投诉提交仍独立确认，提交时复验归属。

`task_plan`节点位于旧`classify_intent`之前，LLM结构化输出最多8项业务任务。安全提醒由独立规则节点前置处理。纯知识/其他单事项可回原单主意图分支，因此不是直接把旧九类分类器改为自由执行的Agent。

V3.1补充受限原文对齐：模型仅改变标点或空白时重新定位实际原文跨度；显式“甲和乙都退款”被拆成单项引用时，只有语法和订单成员关系都通过校验才能复原整段并列原话。数字变化、语义增删、否定及跨任务借号仍拒绝。引用只有订单主语时，也核验紧邻的明确动作。本地受影响核心、图、工具及API共259项通过。

同120场景的V3真实回归资料保存在`data/multi-intent-eval/20261103-binding-v3/`；题目、标注、评分及知识快照保持原样，旧V2三轮轨迹保留，新V3三轮重新调用。此集已用于开发诊断，是回归集，不是独立盲测。V3多余选单88→16，但必需目标732→727，未达到完成率不降要求；该结果保留。V3.1在`data/multi-intent-eval/20261104-binding-v31/`独立冻结后三轮共360次：多余选单88→18，目标732/774→735/774（另2项目标待定），场景325/360→328/360（另1场景待定）。订单/物流/退款/投诉分项各自与V2持平，新增3项来自知识问答；三诉求自动评分40/45→36/45，三轮均通过104→103，不能描述为稳定性全面提升。详细口径、分项及残余漏项见该目录`COMPARISON.md`。


### 跨轮订单指代与客服输出（#132修复）

`business_context`独立保存已核验订单对象及带来源消息ID的用户故障陈述，不保存操作确认或可复用授权。新轮重建task_plan前，从上一checkpoint及归属校验过的历史计划中恢复。旧会话也可由user_selection绑定记录回填，取消退款不删除已讨论的订单。

规划器仍只识别当前消息中的任务；`order_context.bind_tasks`再解析“刚刚的订单”“它”等明确指代。同一原文指代组的订单查询、物流查询和相关售后咨询承接同一对象；如果历史没有唯一对象，一次选单仅在该指代组内共享，不给独立的退款或“另一笔订单”借号。执行时仍复验归属，状态和物流重新查询，不复述旧业务结果。多订单歧义及无关商品保留澄清。

知识问答同时获得本次读取的商品/订单信息和明确标注为用户陈述的故障。针对退货资格咨询，先检索适用的质量问题/一般退货政策，再结合这些资料条件化回答；政策证据不等于具体订单资格获批，保修也不等于退货批准。原置信度及证据充分性检查保持。不得因历史退款意愿恢复已取消操作或跳过新确认。

task_finish不再把内部状态列表生成为客服答复，用户只收到实际查询、政策解释及确认回执。旧summary事件不再回放；启动时只将有对应内部summary记录的助手消息标记为内部展示项，历史API和模型对话排除它，原文与审计行保留，不按词语删除普通用户/助手内容。

专项证据见`data/verification/conversation-132-fix/`：306项本地测试通过；真实模型/RAG/MCP使用合成会话和隔离SQL验证了首次选1001后，跨连接重建的三事项追问零重复选单。原#132仅做只读回填核查与旧内部消息展示标记，不追加测试消息。没有重跑120场景，不把旧指标视为此次修复的新成绩。

`tasks.py` 的链路为：安全提醒 → 完整计划 → 调度 → 独立业务处理 → 调度 → 等待各项确认 → 创建工单/取消 → 汇总。确定性优先级为订单/物流只读查询、退款、投诉、知识问答，确保已知订单的查询能在退款缺参选单之前完成。退款缺参时先保存等待状态，再在独立节点 interrupt；用户选择并复验归属后继续退款，之后续办投诉。某项失败或取消不会取消兄弟任务。规则已识别的安全提醒不依赖规划模型成功。

这一版没有让 Agent 自由决定多任务写操作：退款政策检索复用 `retrieve_policy`，订单校验复用现有 mock 业务数据；确定性流程只提供人工审核工单入口，不根据检索片段自动承诺退款资格，也不执行资金退款。待付款订单只提示无需退款。政策查询不可用时，退款任务失败并继续其他事项。订单/物流通过注册表及原工具执行引擎调用只读工具，保留归属校验和审计，事实答复由真实字段格式化；缺字段或失败不使用历史猜测补齐。知识任务按独立query检索，经过证据门禁后仅根据证据生成，不授予写工具权限。

`task_plan` 按稳定任务键保存任务，ID来源是会话ID、原始用户消息ID及任务键；重复类型使用 `refund:2` 等独立键，不再互相覆盖。每项独立保存参数、阶段、状态和操作ID；每次准备选单清除共享临时选单结果。图状态保存执行位置与待确认信息；SQL记录保存计划历史、稳定助手消息和工单回执。调度只取PENDING，不重复执行DONE、CANCELLED、FAILED或WAITING_USER。新用户轮将旧未完成计划标记 SUPERSEDED；旧卡片受当前消息水位及 interrupt_id 校验约束，不会被新问题默默授权。

WAITING_USER 区分阻塞选单与非阻塞的工单确认。退款审核和投诉分别确认；任务DONE表示本应用已完成相应步骤，不代表售后处理完结。最终汇总明确写明工单待人工处理及尚未资金退款。

## 投递和一致性

`workflow_records` 用稳定字符串主键保存事件/计划/操作。事件和助手消息在同一事务写入；事件序号使用对应消息ID。前端按 message_id upsert，渲染后ACK；ACK只证明页面发出确认，不证明人已阅读。

`GET /api/conversations/{cid}/task-events?user_id=...&after=...` 支持游标回载。回载校验会话归属，返回事件及仍有效的最新中断。前端重开会话时先载历史，再补齐事件和卡片。

SSE适配器在观察到中断后继续消费图流直到收尾，待checkpointer写入完成才发送操作卡；否则立即断流可能让卡片比持久化状态先到达。普通 actions 也在中断前发送。非流式接口从已保存事件投影当前计划答复，并返回 task_plan。

SQLite checkpoint与MySQL不在同一个事务中。工单写入和成功回执位于同一MySQL事务；checkpoint落后时重跑任务以相同operation_id读取原ticket_no，再推进状态。事件写入也按稳定键去重。

开启开关后，Agent建单通过执行引擎的ContextVar注入稳定操作键；两类表单接口要求request_id，前端对同一按钮/同一参数重试复用它。操作参数哈希不一致返回冲突。会话行锁串行化写入，同一事务创建工单与回执；取消后不能用同一操作标识再次提交。

本地身份仍是演示user_id约定，不构成登录认证。MCP外部写入尚未实现远端幂等键与UNKNOWN对账，这项保证只覆盖本地tickets事务。

## 本地测试开关

打开`http://localhost:8000/`，右上角“多意图”开关关闭时走单主意图路径，开启时走任务计划路径。选择保存在浏览器；切换会自动开始新对话，避免历史上下文影响对照。旧对话不删除，选择历史时恢复该会话模式，暂停任务仍能按原模式继续，无需重启。

`/api/chat`和`/api/agent`接受可选严格布尔值`multi_intent_enabled`。未传时沿用已有会话模式，新会话回退到环境默认值。模式写入SQLite checkpoint，并由请求作用域ContextVar供工具写入策略使用，不修改全局settings。两种模式的并行请求互不影响；已有会话若要求切换模式，在追加用户消息前拒绝并提示新建会话。`GET /api/conversations/{cid}/workflow-mode?user_id=...`核验归属后提供模式回载。

启动时准备工作流表和退款枚举，以支持运行中启用多意图。单意图仍使用原路径，不因其他会话开启多意图而改变写入策略。284项核心/图/工具/API测试通过，其中实际SQLite/MySQL测试覆盖双模式隔离、模式冲突拒绝及暂停任务跨连接重建恢复。浏览器验证另记在`data/verification/local-mode-switch-20261104/`。

用户对照报告只展示单意图基线与最新多意图：`data/multi-intent-eval/20261104-single-vs-latest/REPORT.md`。能力指标沿用原始单意图轨迹与最新V3.1轨迹，页面开关本身未再次运行360次模型评测。

## 环境默认值与部署回退

1. 先备份业务数据库与checkpoint，审核安全模板，完成真实政策资料下的验收。
2. 设置 `MULTI_INTENT_ENABLED=true`，重启服务。启动时幂等创建workflow_records，并检查tickets.ticket_type是否支持退款；旧MySQL表缺少该枚举值时保留原值并追加。
3. 观察多诉求、普通单意图、事件重放和工单幂等。旧图节点仍保留，单意图旧中断可以按原路径处理；旧表单缺少request_id会提示重新打开。
4. 回退前先处理或取消正在等待的新任务。关闭开关后新请求走旧图，事件回载入口不提供新任务卡；不要在仍有待办时盲目关闭开关并期望原卡可继续展示。
