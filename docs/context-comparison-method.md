# 客服上下文对照实验的方法

本实验用于比较客服场景中的上下文策略，不修改线上策略、阈值、数据库或知识库。入口为 `scripts/eval_context_comparison.py`，离线审计入口为 `scripts/audit_context_comparison.py`。Gitee正式结果保存于 `data/ch07/context-comparison/20261016-gitee-v1/`，先前因余额不足中断的目录和单条烟测不混入正式指标。

2026-10-16本轮首跑与一次补跑均已结束，768条评分及离线审计齐全，但仍有15次追问阶段超时和16次去重后的记忆维护超时。`complete=true`只表示案例齐全，不表示接口无故障。完整系统结果见该目录的`audited_report.json`；无调用错误的共同子集为27条会话、每组54次追问，见相邻`20261016-gitee-v1-paired-clean/`目录。共同子集按八组调用错误记录筛选，未按答案正确性筛选，仍存在选择偏差。`FINAL_SUMMARY.md`和`FINAL_STATUS.json`同时说明两个口径、残留失败和成本边界，不将超时混作策略能力差异。本轮没有证明Harness迁移方案显著优于当前方案。

## 场景与输入隔离

数据为48条程序生成的合成会话，八类场景各六条：早期订单、早期商品、两次订单更正、当前话题切换、多跳称呼、承诺日期更新、否定与改选、歧义澄清。每类包含24/40/64轮各两条。每条在第18轮与末轮各追问一次，共96个追问。两次追问共用同一段历史，不能当成96条独立会话。

标签由案例构造规则确定，先于模型调用冻结。摘要、结构化状态和Harness检查点只接收当时已经出现的历史；不接收追问、答案标签或工具数据库。两次追问产生的回答不写入后续历史，这是固定轨迹回放，不是动态用户模拟。历史中的普通回复由固定语料提供，未调用模型重新生成。

## 被测组

|代码|策略|实现范围|
|---|---|---|
|A_full|完整历史|全部已出现原文|
|B_recent6|当前仅滑窗|生产历史助手的3000近似Token窗口，指代模块再取最近6条消息|
|B_window3000|较大滑窗|指代和读取器均使用全部3000近似Token窗口|
|C_current|当前摘要加滑窗|生产compute_boundary、summarize_dialog、_history_text和_agent_messages|
|D_state|结构化状态加滑窗|同样的消息数触发与近期原文，使用带来源消息id、有效性标记的原子事实|
|E_state_retrieval|状态加原文检索加滑窗|与D完全相同的状态，增加中文bigram/编号BM25及匹配事实来源辅助的历史轮检索，最多4段|
|H_original|Harness原提示词迁移|读取外部源码中的原始八章节英文提示词与检查点前言，按Token压力替换早期原文|
|H_customer|Harness客服适配|相同替换/保留规则，章节改为客服实体、指代、修正、承诺、当前对象等|

外部源码来自用户提供的 `D:/harness/deepseek-harness`，仅只读。对应文件、SHA256和原始提示词已保存。未启动其TypeScript应用，也未声称完成其运行时、事件日志、溢出重试、图片卸载或工具结果裁剪的完整复现。

Harness本地源码的默认模型容量为1,000,000 Token，默认thresholdRatio=0.8、retainRatio=0.16。本集远低于默认80万触发点，因此默认文本上下文策略等价于A，不重复调用并虚构独立实验。H两组使用3750的项目近似容量，即3000触发点和600近期保留预算，帮助观测压缩行为。压缩结果必须小于被替换前缀，截断或无缩减均按失败记录。纯文本回放额外按完整用户/客服消息对保留，不涉及工具调用配对。

这些是可比较的迁移设置，非严格等Token实验：生产C/D的摘要在原文窗口之外追加；不同语言和结构的摘要，上游实际Token数也不同。报告使用上游实报用量，不能将近似阈值当成真实模型容量。

## 统一服务路径与评分

每个追问都调用生产 `coref.resolve`，再使用相同的客服规划器选择logistics/care/recall/clarify。物流和清洁说明由合成只读后端按模型给出的订单号/型号返回，后端不会替模型选择正确目标。然后使用同一个回答模型组织最终回答。此路径隔离检索与工具数据差异，不是完整生产LangGraph、真实Milvus知识库或真实业务接口的验收。

任务规则通过要求三个模型阶段成功、行动类型正确、订单或型号正确、最终回答包含必要事实锚点，且不串入其他订单。物流检查订单号及唯一运单号；清洁说明检查型号、断电和软布两个公共操作点；时间承诺检查最终有效日期且不混入旧日期；歧义问题要求澄清，不擅自查询。指代指标单列，不能代替最终任务指标。规则并不覆盖自然语言回答的全部语义质量。

共享读取器温度为0；生产指代、当前摘要和其他记忆策略均使用0.3。每个追问每组仅采样一次，温度0也不保证服务端逐字确定。每条会话按固定随机顺序执行八组。API并发为8，队列等待时间单独记录，阶段耗时不含评测器排队。

## 用量、延迟与统计

每组用量包含该组全部历史维护，以及两次追问的指代、规划和回答调用。原始模型输入输出、上游Token、缓存Token和耗时均保留。D/E共享一次状态抽取以隔离检索变量，但比较独立部署时维护成本各记一次；报告另外提供去重后的实际总调用用量。

这里的成本是本次固定历史回放工作负载的成本，不能称为所有24～64轮都在线生成时的完整会话成本。历史普通回复生成、真实检索网络延迟、向量建库和在线异步调度未测。摘要在回放检查点前等待完成；P50/P95为追问三个模型阶段的总时间，维护耗时另列，不能据此声称线上异步响应更快。

报告按八类场景分别统计，并用整条会话为采样单位，对相对当前C方案的任务通过率差做配对bootstrap区间。两次追问不会被拆开重采样。每类只有一个生成场景族的六个变体，区间不代表跨场景族泛化，也不能将小差异直接宣称为显著优势。

## 运行与复算

```powershell
# 新实验必须使用新目录；源代码、模型配置、数据不同会拒绝续跑旧目录。
.\.venv\Scripts\python.exe -m scripts.eval_context_comparison --output data/ch07/context-comparison/rerun-01 --concurrency 8 --case-workers 8

# 以下均不调用模型。
.\.venv\Scripts\python.exe -m scripts.eval_context_comparison --output data/ch07/context-comparison/20261016-v2 --recompute
.\.venv\Scripts\python.exe -m scripts.audit_context_comparison --output data/ch07/context-comparison/20261016-v2
.\.venv\Scripts\python.exe -m scripts.audit_context_semantics --output data/ch07/context-comparison/20261016-v2
```

最终指标以目录中的 `audited_report.json` 和 `AUDITED_REPORT.md` 为准，原始 `report.json`、逐条输出及初始评分保留。初始规则误将清洁回答中商品自身所属的订单判成串单，`audit_context_semantics` 根据已出现的型号与订单关系，对所有方案统一修正；其他订单仍被拒绝。审计同时规范bootstrap采样顺序，避免集合遍历随机性影响离线区间。离线审计检查数据/源码快照、全部逐条评分、因果检查点、状态来源、D/E状态一致性及用量完整性。真实重新调用模型不保证得到相同百分比，离线复算应得到同样的审计报告SHA256。

## 接口不可用与更换接口

首次正式批跑因接口返回402余额不足中断，该目录不构成完整结论。`scripts/resume_context_comparison.py` 支持低并发、请求间隔、单次健康检查和接口错误熔断。`--repair-only` 只在本地归档接口失败记录并保留有效检查点，不调用模型；语义答错不作为重跑理由。

更换模型或接口时必须新建目录，全部方案重新运行，不与旧服务商的结果混算：

```powershell
.\.venv\Scripts\python.exe -m scripts.resume_context_comparison --new-run --output data/ch07/context-comparison/new-provider-01 --concurrency 4 --interval 0.75
```

新目录另外记录接口域名、模型、启动器源码和散列，不保存密钥。归档的失败尝试属于额外物理开销，不能假装没有发生；其Token不能混入架构能力指标。
