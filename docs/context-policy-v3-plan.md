# DeepSeek V4-Flash 客服上下文方案及预先固定的对照计划

日期：2026-10-23。状态：实验模块，未接入正式客服图。先完成对照，再决定上线方案。

## 工程方案

1. 当前会话短于原文预算时保留完整原文；超过预算时按完整轮次裁剪。
2. 轻量状态只索引当前会话的订单、型号、日期、更正及对象选择原文。保留消息来源与时间顺序，不调用模型反复改写全部事实。
3. 当前对象仅识别明确的字面表达；有歧义时保留原话，不强行填槽。用户陈述不是业务工具验证结果，状态不授予退款或提交权限。
4. 历史追问触发本地关键词和实体回查，优先补充最早记录、最新更正及相邻客服回应。
5. 动态订单状态仍需业务工具查询；公共知识库检索与私人会话历史回查应分开。
6. 本次候选暂不增加摘要。先验证原文加来源状态能否满足场景，再决定是否为超长背景引入摘要。

`app/core/context_policy.py` 是纯函数与本地状态模块。调用方必须传入已完成权限检查的单会话可见前缀。尚未实现生产持久化、跨进程并发更新、完整自然语言槽位解析及动态授权状态机。

## 四组

|组|内容|
|---|---|
|C_current|当前摘要提示词、30条消息触发规则、保留8个用户轮次、3000近似Token历史裁剪、指代最近6条消息；统一使用本实验输出上限|
|W_raw8k|8000估算Token的原文窗口；指代与下游读取相同历史范围|
|S_state8k|W + 上限1800估算Token的来源状态|
|R_recall8k|S + 上限1800估算Token的按需历史回查|

W/S/R 使用显式中文字符估算，不是供应商精确tokenizer。与旧方案的预算计数算法不同，属于整体策略对照，不能把差值只归因于窗口数值。每次非摘要请求加入系统提示词与schema后的估算输入必须不超过16000；API实报输入另外统计。

统一调用 Gitee `DeepSeek-V4-Flash`，关闭供应商自动模型故障转移。最初仅设置`thinking.type=disabled`仍有思考Token；校准后正式实验同时设置`enable_thinking=false`，逐请求保留回执，最终以审计汇总的reasoning Token为准。指代输出上限512，规划1024，回复1536，摘要1024。指代和摘要温度0.3，规划和回复0。使用当前项目模型调用池，背景优先级，最终实验最多8个并行调用。各会话及组别顺序固定随机化。

2026-10-23预检发现强制命名工具选择返回空参数，而auto正常。正式测试统一使用auto、附加只控制响应格式的工具输出要求及Pydantic校验。原始失败与四种协议组合保存在data/verification/context-policy-v3-protocol/。因此C代表当前记忆策略在统一兼容调用器下的结果，不是未经改动的线上端到端结果。

## 数据与可比性

使用已封存48条合成会话回归集，8场景族，每条24～64轮，每条两个因果追问。共384条结果、1152个追问阶段请求，另加C组滚动摘要维护。所有组重新生成，不与旧结果拼接。

这是已知模板回归集，不是独立留出集。历史文本由数据集给定，不生成全部历史轮次。只读工具结果由固定夹具返回，不访问真实订单、Milvus或生产会话库。本实验不支持生产正确率、全会话成本、写操作安全率或未见场景泛化的结论。

## 固定评分与失败处理

同时报告旧严格规则与新规则。新规则仅额外允许明确标为作废/未使用的旧编号或日期出现在答复中。错误的实际工具目标始终失败。不因答错而重试。

分别报告指代、行动/对象、最终规则通过、空回答、输出截断、解析失败、接口失败。最多对传输异常立即重试一次；原始尝试全部保留。空回答、截断或非法结构化输出不自动重试。

Token记录覆盖所有本次维护与两次追问的输入输出；接口失败可能缺失计费回执，不能声称账单完全精确。缓存命中用量保留在逐调用文件。背景状态处理CPU时间单列。延迟为指代、规划、回答阶段累计，排除实验等待队列与异步维护，不等于线上首字延迟。

## 完成与选择标准

### 协议校准阶段

首阶段`20261023-gitee-v3`在53条追问、207个阶段请求后停止并封存。56次改写中17次达到512Token上限；不把该阶段当作完成的能力对照。诊断证明该接口仅收到`thinking.type=disabled`仍产生思考Token，而同时设置`enable_thinking=false`后短请求思考Token为0。

第二阶段`20261023-gitee-v3-nonthinking`四组统一增加`enable_thinking=false`，从头运行。84条追问后发现新增调用器把额外格式指令放在末尾system消息，摘要频繁重复该指令。对4条固定失败输入做格式对照：末尾system成功1/4，合并入开头system成功4/4。该阶段439次已完成调用全部保留，停跑时未完成的请求可能缺失计费回执。不能用该阶段对上下文能力排名。

最终目录为`20261023-gitee-v3-initialsystem`。修正为单个开头system消息；四组输出预算、记忆策略、评分与数据不变，不复用前两个阶段的回答或成绩。最终统一8路并发；前两阶段为4路，不能混算时延。协议调整只在隔离实验调用器，未改线上配置。

必须具备48×4×2条结果，逐条评分可离线复算，数据和源码快照一致，状态及回查不含未来消息。使用整会话配对bootstrap，不把同会话两个追问视作独立样本。报告按场景细分与接口失败，不只给总体排名。

优先选择对象选择与最终回答都可靠、维护开销低的最简单方案。若差值不确定，不宣称显著提升。即使回归全过，也需另行验证真实客服流程、独立新场景与响应时延后再上线。

## 后续生产接入设计（未实施、未计为本轮效果）

- **事实优先级**：当前业务工具结果用于动态订单事实；用户明确更正用于本轮对象选择；历史客服表述只能作为待核实线索。按订单/商品/诉求分别绑定来源和修订版本，禁止跨对象覆盖。
- **对象歧义**：多笔订单且用户未选定时，工作流应返回澄清，不让改写器自行填入一个编号。撤回或取消申请必须清除待执行动作；退款、退货提交仍经过原有权限与确认流程。
- **输入预算**：生产预算必须包含系统提示词、工具schema、RAG证据、工具结果与历史。测试中的16000估算上限仅覆盖只读夹具工作负载；接入真实RAG后需给证据预留空间，再缩减历史与补充回查，不能直接把四个预算相加当生产配置。
- **状态持久化**：按会话和租户隔离；记录消息边界、策略版本和版本号；并发更新使用乐观锁。失败保留上一版本及原文，不覆盖为未经验证的模型摘要。
- **延迟控制**：明确给出对象的独立问题可考虑跳过指代改写；含糊追问才读取完整关系证据。这个优化本轮未测，不能把预估节省写成实测。
- **发布门槛**：先修复真实接口参数与结构化输出兼容；用独立新会话覆盖订单切换、更正、撤回、歧义、RAG和真实工具；统计完整链路首字/完成P50/P95、对象误选率和接口错误。通过后再小范围切换，保留当前策略回滚入口。

DeepSeek官方模型卡标示百万Token上下文，但这不能替代供应商部署的限制和本项目延迟验证。本方案把长窗口作为可用余量，不将百万Token原样塞入每次客服请求。参考：https://huggingface.co/deepseek-ai/DeepSeek-V4-Flash 。
