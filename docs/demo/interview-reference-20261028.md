## 1. 开场：先介绍客服实现了什么

**操作：**打开 [GitHub 首页](https://github.com/Orange-ui0811/caremate)，停留“系统做什么”。

> 我介绍一下智能客服项目。它是一个面向电商场景的智能客服，现在主要支持商品咨询、订单和物流查询，以及退换货、售后这些服务。
>
> 客服整体架构是 LangGraph 编排的 Workflow和核心是通过 Function Calling 实现的工具循环agent。
>
> 它主要涉及四个组件：LangGraph 负责把流程串起来，LangChain 负责组织模型调用，MCP 接入独立业务工具，Langfuse 用来查看运行记录。

## 2. 从一条用户消息，讲清整个 Workflow

### 2.1 LangGraph：先决定这条问题应该怎么处理

**操作：**打开 [Workflow 文档](https://github.com/Orange-ui0811/caremate/blob/main/docs/architecture/workflow-and-agent.md)，停留“九类意图与五个处理分支”，再点 [build.py 的 `_builder`](https://github.com/Orange-ui0811/caremate/blob/fcfdd419b4736a189e65b7cee2fdd52691fb194e/app/graph/build.py#L8)。

> 先看用户发来一条消息以后，系统怎么走。
>
> 最前面是指代补全和意图识别。比如用户只说“那一单到哪了”，先尽量结合历史把对象补出来，再判断他要查物流，还是退货、咨询商品。这里识别九类主意图，但后面归到五条处理路线。
>
> 商品咨询必须先查知识库，再检查证据。退款退货和售后必须先取得订单，再查政策。订单、物流和人工服务进入主 Agent，由模型根据需要提出工具请求。投诉走固定安抚和服务入口，闲聊、其他走固定引导。

**操作：**指 `StateGraph(ConversationState)`、`add_edge`、`add_conditional_edges`，最后指 `agent_tools → main_agent`。

> 对应到代码，`StateGraph` 定义这张图，消息、意图、订单和检索证据都保存在共享状态里。`add_edge` 连接必须执行的下一步，`add_conditional_edges` 根据状态选择分支。
>
> 主 Agent 如果返回了工具请求，就进入 `agent_tools`，工具结果回来以后，再回到 `main_agent`。模型会根据结果继续调用工具，或者组织回答；没有工具请求，或者达到步数上限，这一轮就结束。
>
> 所以这里是固定工作流配合一个主 Agent。需要保证的顺序写在图里，工具怎么组合则留给模型。比如退款一定先取单再查政策，但普通物流问题里，查订单、再查物流这两个工具的组合，是模型根据数据依赖决定的。
>
> 图把下一步去哪规定好了，那每个节点具体怎么向模型提问、怎么拿到可供程序使用的结果，就要看 LangChain 这部分。

**备答：**确定性指流程约束，节点内部仍可能调用 LLM。当前一次输出一个主意图；步数上限控制主模型调用次数，达到上限不代表业务完成。停止判断见 [should_continue](https://github.com/Orange-ui0811/caremate/blob/fcfdd419b4736a189e65b7cee2fdd52691fb194e/app/graph/routing.py#L30)。

### 2.2 LangChain：从提示词变量，讲到解析结果和绑定工具

**操作一：**打开 [prompts.py 的 `INTENT_CLASSIFY_PROMPT`](https://github.com/Orange-ui0811/caremate/blob/fcfdd419b4736a189e65b7cee2fdd52691fb194e/app/core/prompts.py#L207)，指向实际代码：

```python
INTENT_CLASSIFY_PROMPT = ChatPromptTemplate.from_messages(
    [("system", INTENT_CLASSIFY_SYSTEM),
     ("human", "最近对话(可空):\n{history}\n\n当前用户这句话:{query}")]
)
```

> 这个项目需要模型完成多种任务：补全用户问题；判断意图；改写检索查询；判断证据是否足够；选择业务工具；根据工具结果生成回答。些任务都会涉及提示词、模型请求、返回结果处理。项目用 LangChain 统一组织这些操作更方便
> 我用意图识别这条链来说明。这里的 `from_messages` 是 LangChain 提供的，它把两段内容做成一个聊天提示词模板。
>
> 第一段是 system 消息，内容来自上面的 `INTENT_CLASSIFY_SYSTEM`，里面写了九类意图的定义和判断规则。第二段是 human 消息，里面留了 `history` 和 `query` 两个位置，分别放历史和当前问题。
>
> 这一步只是定义模板，还没有调用模型。真正填内容和发请求的地方在 `intent.py`。

**操作二：**打开 [intent.py 的 `classify`](https://github.com/Orange-ui0811/caremate/blob/fcfdd419b4736a189e65b7cee2fdd52691fb194e/app/core/intent.py#L19)，指下面几行，再向上指 `_Intent`。代码摘录省略了外围异常处理：

```python
model = llm.structured(_Intent, model=settings.intent_model or None)
r: _Intent = await (INTENT_CLASSIFY_PROMPT | model).ainvoke(
    {"query": query, "history": history or "(无)"})
```

> 看这里传给 `ainvoke` 的字典，`query` 和 `history` 就会填进刚才模板里同名的位置；没有历史时填“无”。中间这个竖线是 LangChain 的调用链组合写法，先让模板生成消息，再把消息传给右边的模型。`ainvoke` 执行这条异步调用链。
>
> 右边的 `model` 也不是随便返回一段文字。第一行把 `_Intent` 这个 Pydantic 结构传进去了，要求结果包含 `intent` 和 `confidence`。`intent` 只能从九类里选，`confidence` 限定在零到一。
> 
**操作四：**打开 [nodes.py 的 `_agent_messages`](https://github.com/Orange-ui0811/caremate/blob/fcfdd419b4736a189e65b7cee2fdd52691fb194e/app/graph/nodes.py#L274)，随后看同页 [main_agent](https://github.com/Orange-ui0811/caremate/blob/fcfdd419b4736a189e65b7cee2fdd52691fb194e/app/graph/nodes.py#L316)。下面只摘出调用主线，省略日志行：

```python
specs = await registry.get_all_specs()
model = get_chat_model(streaming=True).bind_tools([s.tool for s in specs])
msgs = _agent_messages(state)
ai: AIMessage = await model.ainvoke(msgs, config)
```

> 主 Agent 这里是另一种调用。`_agent_messages` 先放一条固定的 `SystemMessage`，再放历史窗口，以及摘要、知识证据和本轮订单等材料，形成消息列表。
>
> 上面这行 `get_all_specs` 取出当时能用的工具，`bind_tools` 把工具名称、说明和参数结构交给模型，然后 `ainvoke` 把这组消息发出去。
>
> 返回的是 `AIMessage`。如果里面有 `tool_calls`，后端才去执行；结果会包装成 `ToolMessage`，用 `tool_call_id` 对应原请求，再送回模型。模型能提出调用，但实际执行、参数校验和用户确认都由后端控制。
>
> 刚才提到的工具，有些是后端本地函数，比如订单查询；还有些运行在独立服务里，比如物流查询。这一部分就通过 MCP 接进来。


### 2.3 MCP：把独立物流服务接到刚才的工具列表

**操作：**先打开 [物流服务的 `query_logistics`](https://github.com/Orange-ui0811/caremate/blob/fcfdd419b4736a189e65b7cee2fdd52691fb194e/mcp_servers/logistics_server.py#L22)，指 `@mcp.tool()` 和 `tracking_no`；再打开 [mcp_client.py](https://github.com/Orange-ui0811/caremate/blob/fcfdd419b4736a189e65b7cee2fdd52691fb194e/app/tools/mcp_client.py#L47)。

> 这是为了模拟真实场景下物流和售后服务可以独立维护，并用统一方式暴露工具名称、说明、参数及执行能力。客服端不用为每个接口都单独设计一套工具接入格式。
> 先看服务端，`query_logistics` 接收的是物流单号。函数加上 `@mcp.tool()`，就通过 FastMCP 暴露出去；这个服务单独启动，使用 streamable HTTP 通信。
>
> 再看客服这边，`MultiServerMCPClient` 保存物流和售后服务的连接，`get_tools` 去发现它们提供哪些工具。适配后得到 LangChain 能调用的工具对象，再和本地工具合并，交给刚才的 `bind_tools`。
>
> 比如用户问订单物流，模型可以先请求订单工具，从返回结果里拿到物流单号，再请求 `query_logistics`。后端检查参数以后，通过 MCP 客户端把请求发给物流服务，结果回来以后再交给模型回答。

**操作：**需要展示执行位置时，点 [engine.py 的 `execute_tool_call`](https://github.com/Orange-ui0811/caremate/blob/fcfdd419b4736a189e65b7cee2fdd52691fb194e/app/tools/engine.py#L101)，指 `spec.tool.ainvoke(args)`。

> 实际执行在这行 `spec.tool.ainvoke(args)`。前面会做参数校验、身份注入和确认检查，外面还有超时和重试策略。MCP 解决的是工具接入，业务权限仍然要由项目自己检查。当前独立服务用的是模拟业务数据，最后可以在本地演示这条调用路径。

## 3. RAG：从知识内容和存储，讲到选型与结果

离线入库：将知识问答按结构切成片段，由embedding模型BGE-M3转成1024维向量写入Milvus；原文也存入向量库，检索命中后直接返回原文。
在线查询:将用户问题补写后，然后向量化进行两路检索：1.向量路径计算与知识片段的余弦相似度，返回相似度最高的50条2.先使用模型扩写问题检索问题，使用Milvus自带的BM25路径根据词项匹配程度计算分数返回分数最高的50条。通过Milvus内置的RRF两路排名融合，平滑常数取60；最终取融合后的前50条。最后使用重排模型bge-reranker-v2-m3重新阅读“问题+原文”选top10；此外还会根据第一候选的重排分数判断当前证据是否足够：大于阈值发给模型问题+10条原文

### 3.1 用什么知识，为什么采用 MySQL＋Milvus

**操作：**打开 [RAG 文档的知识入库部分](https://github.com/Orange-ui0811/caremate/blob/main/docs/architecture/rag-and-confidence.md)，再打开 [data/kb](https://github.com/Orange-ui0811/caremate/tree/fcfdd419b4736a189e65b7cee2fdd52691fb194e/data/kb)。

> 先看知识内容。这里以宠物用品电商为示例，资料包括商品规格、常见问题、退换货政策、售后手册，以及会员权益、运费和发票规则。订单和物流这种会变化的数据另外走工具查询，知识库主要保存这些相对稳定的说明和规则。
>
> 存储上用了 MySQL 和 Milvus。MySQL 保存知识原文、分类、章节路径和处理状态，方便后台编辑和审核；Milvus 负责把这些片段检索出来。两个存储用同一个知识 ID 对应，查到片段以后才能找到它的原文来源。

**操作：**打开 [milvus_client.py 的 `ensure_collection`](https://github.com/Orange-ui0811/caremate/blob/fcfdd419b4736a189e65b7cee2fdd52691fb194e/app/kb/milvus_client.py#L41)，指 `dense`、`text`、`sparse` 和 `FunctionType.BM25`。

> 选择 Milvus，从当前实现看，它支持稠密向量、内置 BM25 和 RRF 混合检索的，能够统一管理检索索引、文本和元数据，并接入审核后的知识增量更新。同时考虑到如果电商系统真正要落地，向量规模会持续扩大，按品种、店铺过滤的标量查询也会有需求。
>
> 存储确定以后，还有一个前提：不能把整份手册直接丢进去，要先把它整理成能够独立理解的知识片段。


### 3.2 怎么分块，为什么保留标题、完整句子和表头

**操作：**打开 [documents.py 的 `build_chunks`](https://github.com/Orange-ui0811/caremate/blob/fcfdd419b4736a189e65b7cee2fdd52691fb194e/app/kb/documents.py#L28)，指标题路径、普通正文和表格分支。

> 分块先按 Markdown 标题切，保留从一级到四级的标题路径。这样检索出来以后，能知道它属于哪个商品、哪一节政策，也能把出处显示给用户。
>
> 普通长正文再递归切分。这里默认基础块是四百个字符，后面补上一块末尾的完整句子，重叠目标大约六十字符。这样做是为了减少“条件在上一块，结论在下一块”的情况；因为优先保留完整句子，最终长度可能超过基础块长。
>
> 表格单独处理，按数据行拆，并给每块保留表头。比如参数表里某个数值，离开型号和列名就没有意义，所以不能只截出几行数字。

**操作：**需要时点 [apply_sentence_overlap](https://github.com/Orange-ui0811/caremate/blob/fcfdd419b4736a189e65b7cee2fdd52691fb194e/app/kb/chunking.py#L44) 和 [split_table_rows](https://github.com/Orange-ui0811/caremate/blob/fcfdd419b4736a189e65b7cee2fdd52691fb194e/app/kb/chunking.py#L72)。

> 入库做向量时，拼的是分类、标题问句和正文，所以向量不只包含正文的一小段，也带着它的主题。资料准备好以后，下一步就是选择把这些文本转成向量的模型。

### 3.3 Embedding 选型：为什么当前保留 BGE-M3

**操作：**打开 [五模型 Embedding 报告](https://github.com/Orange-ui0811/caremate/blob/main/docs/evaluation/embedding/README.md)，先看输入协议，再看总结果与 E 桶。

> 项目当前用 BGE-M3，优先考虑了开源的模型BGE-M3：中英文都能检索，能处理8192token的文本，检索能力稳定；输出固定1024维向量。这里有一份五模型对照可以说明选择依据。除了 M3，还比较了 BGE small、BGE large，以及 Qwen3 Embedding 的零点六 B 和四 B。
>
> 比较时固定同样的五十二个知识片段和三百道题，各模型分别生成向量，归一化以后直接算余弦相似度，再看前几名有没有覆盖需要的知识。这里没有加 BM25、重排或答案生成，所以主要检查 Embedding 本身的检索表现。
>
> 看结果，M3 的分组 Recall@5 是百分之九十八点九六，跨文档那一桶是百分之九十五点八三，在这份题集里表现比较好。Qwen 零点六 B 的分组倒数排名更高，说明不同指标并不是同一个模型全赢。
>
> 对这个项目来说，先把需要的证据召回来很重要，后面还可以重排，所以这份结果支持继续保留 M3。不过这些是当前小语料上的结果，没有证明换一个业务场景仍然最好。
>
> 模型选好以后，在线检索也没有只用向量这一条路。因为客服问题里既有口语表达，也经常有型号和具体术语，所以还组合了 BM25 和重排。

### 3.4 实际怎么检索：向量＋BM25 → RRF → 重排

**操作：**打开 [retrieval.py 的 `search_knowledge`](https://github.com/Orange-ui0811/caremate/blob/fcfdd419b4736a189e65b7cee2fdd52691fb194e/app/core/retrieval.py#L51)，依次指 query 向量化、`hybrid_search` 和 `rerank.rerank`。

> 以一条普通商品问题为例，先把问题变成向量，去找语义接近的知识。比如用户说“东西不想要了还能退不”，资料里可能写的是“七天无理由退货”，向量检索用来补这种说法差异。
>
> 同时走 BM25。像 MH-LP100 这种型号，或者“保修期限”这种词，字面匹配也很有用。代码默认两路各召回五十条，再用 RRF 融合成候选列表。

**操作：**点 [milvus_client.py 的 `hybrid_search`](https://github.com/Orange-ui0811/caremate/blob/fcfdd419b4736a189e65b7cee2fdd52691fb194e/app/kb/milvus_client.py#L111)，指两条 `AnnSearchRequest` 和 `ranker=RRFRanker()`。

> 这里一条请求查 dense，一条查 sparse。`RRFRanker` 根据片段在两路中的排名来融合，不直接把余弦分数和 BM25 分数相加，因为这两种分数的尺度不同。
>
> 融合后再回到 `search_knowledge`，把问题和候选文本交给 BGE-Reranker-v2-M3 精排，默认取前十条。召回先尽量把相关资料找全，重排再判断这些候选里哪些更贴近当前问题。

**操作：**补充查询处理时，打开 [retrieve_knowledge](https://github.com/Orange-ui0811/caremate/blob/fcfdd419b4736a189e65b7cee2fdd52691fb194e/app/graph/nodes.py#L180)，指 `standard`、`expanded` 和 `bm25_text`。

> 检索前还会整理标准问法和扩展词。对于没有被拆分的单问，标准问法用于向量和重排，扩展词追加到 BM25 文本。遇到一条消息问好几件事，代码还会按子句分别检索重排，再轮流合并、去重，避免一种诉求把结果占满。
>
> 不过这些设计有没有帮助，不能只看流程图。下面这份四策略报告，就是把向量、BM25、混合、混合加重排放在同一套题里比较。

**备答：**Top50/Top10为代码默认，部署可调整。子句分支分别检索后合并，没有对最终合并列表再做一次全局重排。公开检索入口仍从原句开始理解，本地已有优先使用补全问题的修改；多轮行为要区分版本。

### 3.5 用什么题测，结果说明了什么

**操作：**打开 [RAG 四策略报告](https://github.com/Orange-ui0811/caremate/blob/main/docs/evaluation/rag/README.md)，先看五桶设计，再看总体表和跨文档列。

> 这份评估共三百题，分成政策、型号、口语、库外和跨文档五类，每类六十题。库外问题单独看拒答，其他四类一共二百四十题计算检索指标。
>
> 跨文档题会故意同时问多个条件，比如“新疆下单八十块钱，会员免运费能不能抵”。这时不仅要找到运费规则，还要找到偏远地区和会员权益的限制。标注里把必需的证据组列出来，缺一组就不能按完整召回算。
>
> 它会用于对比纯向量、纯 BM25、混合检索以及混合检索加重排四种策略，主要看 Recall@5 和 MRR。Recall@5 衡量所需证据是否进入前五条，MRR 衡量正确证据的排序位置。以及计算置信度阈值，它会记录不同候选最高的有效重排分可答题通过率和拒答题通过率



### 3.6 证据够不够：两道检查再进入回答

**操作：**回 [retrieve_knowledge](https://github.com/Orange-ui0811/caremate/blob/fcfdd419b4736a189e65b7cee2fdd52691fb194e/app/graph/nodes.py#L180)，指 `compute_evidence_confidence` 和 `selfcheck.check_sufficient`；需要时点 [评分函数](https://github.com/Orange-ui0811/caremate/blob/fcfdd419b4736a189e65b7cee2fdd52691fb194e/app/core/confidence.py#L22)。

> 这里先做数值检查：取最终候选中最高的有效重排分，和运行阈值比较，太低就进入兜底。这版已经把以前的四信号加权换成最高重排分，让分数含义更直接，也避免受合并顺序影响。
>
> 通过以后，还会把问题和候选资料一起交给 `check_sufficient`，让模型判断证据是不是足够。因为最高分只能说明有一段比较相关，用户同时问的其他条件仍然可能没覆盖。
>
> 两道检查都通过，才整理带编号的证据交给主 Agent；没通过，就给出兜底回复，并保留问题和召回快照。阈值在管理端可以持久化修改，最后演示时可以看到它对可答通过和应拒放行的影响。
>
> 前面这些解决的是“当前问题查什么资料”。但实际聊天里，用户经常只说“那件”“换一单”，检索前得先弄清他说的是谁。下面就讲上下文怎么处理。

## 4. 上下文：先把用户说的对象找对

### 4.1 为什么同时保留摘要、近期原话和回查

**操作：**打开 [上下文工程说明](https://github.com/Orange-ui0811/caremate/blob/main/docs/architecture/context-engineering.md)，停留三类材料表，再点当前实现代码摘录。

> 上下文这一块，当前用了滚动摘要、近期滑窗，再加相关原文回查。
>
> 原文保存在数据库；滑窗保留近期表达，减少压缩损失；摘要保存较早的背景；原文回查补充摘要可能遗漏的对象关系、更正和限制。摘要边界之后累计30条消息时，在当轮回复结束后后台更新摘要，成功后保留最近3轮原文。每次收到问题，再用本轮原话对当前会话的历史用户问句做BM25检索，取正分Top3，并带上前后相邻问答。最后按消息ID与各节点已有原文去重，携带来源引用。
>
> 比如用户先说一个订单，过一会儿更正了号码，之后又聊了别的事。最后他说“查一下更正后的那单”，系统需要保留的不是两个孤立号码，而是谁被更正成了谁。

**操作：**在 [新回查代码摘录](https://github.com/Orange-ui0811/caremate/blob/main/docs/architecture/code-excerpts/context-recall.md) 中找到 `dialogue_supplement`，依次指 `rows[:-1]`、`ranked[:3]`、`index-1/index+1` 和 `not in visible`。
>

**备答：**这是当前本地实现摘录，公开`app/`尚未完整同步。默认新增30条消息后尝试后台维护摘要，成功后留3轮；coref/intent截最近6条历史消息，回答原文窗口约3000估算Token，摘要、回查和系统材料另计。历史客服说法不能替代本轮业务回执。

### 4.2 题目怎么设计，怎么判断是否完成任务

**操作：**打开 [四方法报告](https://github.com/Orange-ui0811/caremate/blob/main/docs/evaluation/context/README.md)的题目设计，再打开 [questions.json](https://github.com/Orange-ui0811/caremate/blob/main/docs/evaluation/context/questions.json)，查找 `unified_early_order_corrected_long`。

> 这里固定二十四段合成会话，每段连续追问三次，一种方法一共检查七十二次任务。包含长短两类历史，也包含更正、对象切换、歧义和用户限制这些情况。
>
> 比如这条，前面把七一零零零一更正成七一零零零三，第一问要求实际查更正后的订单。第二问明确换成七一零零零四，第三问再说“新换的这张单”，要求刷新物流。
>
> 判定时不只看答案有没有写对编号，还看工具实际查的对象和本轮回执。每种方法上一问的真实回答也会进入自己的下一问，所以测的是连续任务。

**操作：**回到四方法表。只念下面引用块，不逐格报数字。

| 方法 | 任务规则通过 | 三问全过 | 全部总 Token |
| --- | ---: | ---: | ---: |
| 完整历史 | 71/72，98.6% | 23/24 | ≥641,440 |
| 仅滑窗 | 34/72，47.2% | 9/24 | 286,962 |
| 摘要＋滑窗 | 59/72，81.9% | 18/24 | 403,048 |
| 摘要＋滑窗＋新回查 | 70/72，97.2% | 22/24 | 479,290 |

>
> 成本上，新混合用了四十七万九千二百九十个总 Token，摘要维护已经算在里面。相比完整历史，至少少了十六万二千一百五十个；按完整历史已记录用量的下界算，大约减少百分之二十五点三。
>
> 但和只用摘要滑窗比，新回查的 Token 增加了约百分之十八点九，所以这里的取舍是多花一些输入，换回更多历史信息。实验用真实模型和图流程，业务服务用隔离夹具，结果反映的是这些内部固定场景。
>
>

**备答：**24段由16条已见回归与8条内部补充组成，不是外部盲测；8短16长，不沿用旧“每条24～64轮”。完整历史有一次超时缺失usage，Token为下界，精确节省比例未知。新混合含44次摘要调用、68,769Token，已计入总量。结果是分阶段单次运行，不主张统计显著性。

## 5. 知识反馈：把没解决的问题变成可审核的知识缺口

**操作：**打开 [知识反馈文档](https://github.com/Orange-ui0811/caremate/blob/main/docs/architecture/feedback-and-classifier.md)，需要展开时点 [flywheel.py 的 `process_pending`](https://github.com/Orange-ui0811/caremate/blob/fcfdd419b4736a189e65b7cee2fdd52691fb194e/app/core/flywheel.py#L38)。

> 客服知识库无法一次性覆盖所有真实需求。仅有RAG检索和生成，只能处理当前已有知识；我希望把未解决问题转成知识维护任务，让运营能够追踪原因、识别高频问题，并把核准答案补回知识库。
>
>问题池主要接三种来源：检索分数太低、生成前判断证据不够，以及用户反馈没有解决。能取得召回结果时，会把当时的片段快照一起保存下来。
>
> 这样审核时就能区分，是根本没有这条知识，还是有知识但没检对，或者资料检到了、回答却没用好。
>
> 后台先把问题标准化，再查重归并，相同问题可以累计次数，帮助判断先补什么。生成的答案只是草稿，必须由人工核准，才写入知识存储并更新检索索引。点一次“没解决”，不会直接把模型答案变成新知识。
