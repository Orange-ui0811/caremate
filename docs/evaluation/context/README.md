# 上下文工程：四种方法对照

展示完整历史、仅滑动窗口、滚动摘要＋滑窗、**滚动摘要＋滑窗＋新回查**四种方法。引用同一冻结的 24 段内部合成会话，每段连续追问三次，每方法 72 次任务判定。三组基线来自 2026-10-27 的运行，新回查混合组来自 2026-10-28；本页整理已有结果，没有新增模型调用。

## 测试的问题怎样设计

### 样本组成

- **24 段均为合成会话**，没有真实客户会话。包含 16 条已见回归与 8 条预先设计的内部补充样例，不能称外部盲测。
- 8 条短会话、16 条长会话。短历史为 8～18 条消息，历史启发式估算 379～810 Token；长历史为 48～106 条消息，估算 2,331～7,538 Token。消息数与用户/客服完整轮数不同。
- 六个基础场景各有短、长版本，共 12 段；再加入 4 条远距指代／别称／相邻更正／歧义回归，以及 8 条普通与困难内部样例。
- 每段三次追问连续执行，某方法自己的上一轮真实回答进入该方法下一轮历史，不能把每问当完全独立样本。
- 历史中加入无关但语义不同的资料咨询，拉开关键事实与追问的距离；目的不仅是背住孤立编号，还要保留“对象—称呼—型号—限制—更正”的关系。

### 主要测试场景

| 场景 | 怎样构造历史和追问 | 正确行为 |
| --- | --- | --- |
| 早期订单更正 | 先登记订单，再更正号码；隔开历史后问“更正后的这张订单” | 使用更正后号码，后续显式换单继续更新 |
| 自然对象切换 | 登记“寄给妈妈”和“工作室”等不同用途 | 按当前诉求切换，不让旧话题覆盖新选择 |
| 商品与部件关系 | 摄影棚对应摄像头，餐厅对应喂食器；分别问镜头、食盆和机身 | 查询正确型号，避免套用另一部件的清洗规则 |
| 限制与部分撤回 | 两笔订单都禁止催单、建工单，后来只撤回其中一项 | 作用对象和动作分别处理；撤回限制不等于授权写入 |
| 多候选歧义 | 历史中保留两个未选定订单，用户只说“这张单” | 先澄清；明确选择、更正后再查询 |
| 最新业务状态 | 旧助手曾有未核实说法，物流夹具按逻辑轮次更新或失败 | 本轮实际查询，并使用当前回执；失败时不拿旧成功冒充新查询 |
| 回查边界与词项困难 | 中间区未被摘要但已离开近期输入；非相邻更正、地点改名或纯指代 | 能恢复关系；缺依据时澄清，不猜对象 |
| 普通显式问题 | 每问都给订单号或型号，近期就能解答 | 检查新机制是否给简单请求增加不必要开销或造成退化 |

完整 24 段的目的、长度、三次问题与预设金标见 [questions.json](questions.json)。它是题目设计目录，不含全部预置历史和逐次运行材料，不能直接当作完整重跑数据包。

### 一条实际用例

`unified_early_order_corrected_short/long`：先登记 710001，再明确更正为 710003；后续三问为：

1. “前面更正后的这张订单，现在运输到哪里了？请实际查一下。” → 目标 710003。
2. “这次换成订单710004，请查这张单目前的物流。” → 目标 710004。
3. “新换的这张订单，再刷新一次物流，告诉我最新进展。” → 仍为 710004，并要求本轮新查询。

不能只检查答案有没有出现正确订单号；还需要核对实际工具查询的对象和当前物流回执。

## 四种方法的输入方式

| 方法 | 历史输入与维护 |
| --- | --- |
| 完整历史 | 使用历史的节点取得全部可见原问答，取消历史截取；查询改写仍使用补全问题 |
| 仅滑动窗口 | 无摘要、无回查；按相同批次边界推进窗口，维护后保留 3 轮，coref/intent 取最近 6 条消息，回答保留原 3,000 估算 Token 窗口 |
| 滚动摘要＋滑窗 | 30 条新增消息触发维护，旧摘要与新滑出原文形成新摘要，维护后留 3 轮；节点输入同上 |
| 滚动摘要＋滑窗＋新回查 | 保留摘要和原窗口，对全部可见历史用户问句做 BM25，取正分 Top3 及各自前后问答；按节点已有原文消息 ID 去重后补入，并附来源 |

“留 3 轮”是维护后的原文保留量；两次维护间消息会累积，不表示每次始终只看 3 轮。3,000 是回答原文窗口目标，摘要、回查、系统提示和工具定义另计，不是整个请求上限。

## 任务判定与成本

实验调用真实模型和 LangGraph/SSE，数据库、知识检索与动态业务工具使用隔离夹具。全部组共享同一业务提示、工具定义及新鲜业务证据检查条件。问题、金标、评分及配置在运行前冻结；金标不传给模型。判断依赖目标对象、实际工具请求、必要事实和对应场景的限制、澄清、时效要求，不将“回答中有编号”单独当成功。

任务规则通过以每方法 72 问为分母；三问全过以 24 段为分母。预设的业务接口失败题可以因正确查询后诚实披露而通过；模型接口错误和未达到任务要求的记录仍留在分母。当前测试不验证完整正向写授权。

全部总 Token 包含本工作负载的摘要初始化、回复后维护及记录到的重试。新混合组 44 次摘要调用、68,769 Token 已包含在 479,290 中，不能重复相加。不包含预置历史逐轮生成以及真实 RAG/业务服务费用，也不是人民币账单。

完整历史有一次证据检查 ReadTimeout，缺失 usage，故标为 **≥641,440**；不能将缺失部分当零。新混合仍有两次限制撤回任务失败，其中一次没有实际查询却输出物流，不能称已解决所有新鲜性问题。

各方法是同模型、同问题与金标、不同时期的独立单次生成；摘要和后续历史会各自演进。该表不是严格同期多重复消融，不证明统计显著性、未见客户泛化或当前在线准确率。模型使用 Gitee DeepSeek-V4-Flash，关闭思考。实验夹具统一开启新鲜业务证据检查，与部署配置应分别记录。
