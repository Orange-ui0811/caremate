# 紧凑上下文验证：运行前声明

日期：2026-10-27。目的：验证按调用职责缩小历史视图，能否降低 Token，同时保留对象识别、更正、撤回及操作限制。此文在新模型运行前写入；已有实验和错误记录不覆盖。

## 比较对象

|组|用途|历史装配|
|---|---|---|
|C|当前 legacy 系统参照|现有摘要与滑窗；保留其原预算与估算器，明确不是等预算组件对照|
|M|上一版来源状态参照|来源状态、条件回查、预算摘要；三个 reader 阶段复用最多 9800 估算 Token 的回答视图|
|CW|紧凑窗口对照|按阶段提供近期原文及已维护的摘要，使用统一估算器|
|CS|紧凑来源状态|与 CW 相同的阶段预算，额外使用有来源的状态、必要原句和既有条件回查|

CW/CS 的预定历史预算为指代 1800、意图 1000、规划/回答 4200。这只是历史材料额度，完整请求仍检查系统提示、工具定义与本轮工具结果，总输入估算上限 16000，输出上限 8192。估算器不是供应商 tokenizer；最终用 API usage 核算。离线检查若发现装配错误，只能在正式冻结前修复并记录，不能按模型得分调参。

M/CW/CS 采用同一摘要触发与维护策略：12000 历史估算 Token 触发，摘要目标 1000，保留近期 8 轮。各组模型维护输出可能存在随机差异，不能把总策略对比说成纯容量的因果效应。

本轮不跳过指代、不合并规划与回答、不修改模型、思考模式、提示词评分规则，也不扩大召回触发规则来针对已知错误。必要状态原句无法装入时必须显式记录预算阻断，不能截掉限制后继续执行。

## 数据和运行

- 公共 reader 使用已见过的 24 条合成回归会话、12 个场景族、每条 3 次追问。12 条 long 使用既有重复背景构造预算压力，非自然客服流量。各组连续回填自身真实输出。
- 相同场景的多个追问相关；不能当成独立样本。按场景族给描述性重采样区间，并列出逐场景退步和改善。
- 当前模型为 Gitee 的 DeepSeek-V4-Flash，关闭思考；复用已验证的强制 ServicePlan 传输协议。保存提示、原始回答、调用失败、usage、来源范围和源码快照。
- 公共 reader 之外增加实际 LangGraph/SSE 流程验证，仍使用合成用户与只读业务夹具，绝不将其称为生产流量或真实 RAG 效果。
- 原 24 条数据是回归集，不能重新命名为未见测试集。新构造压力案例也只称补充验证，未经过独立人工标注。

## 计量与判断

主要计量是原有任务规则通过数及全部有回执的输入＋输出 Token，包含摘要维护和失败重试；缓存读取属于输入，不重复相加。另列对象/动作错误、错误实体、接口/协议/预算故障、不同阶段成本、短长会话分层和真实流程延迟。

首先观察 CS 相对 M 是否节省至少 20% 总 Token，并检查是否增加对象混淆、约束丢失等错误。这是工程目标，不是预定结论；即使通过数相同，单次小规模合成运行也不能证明无损或等价。是否非劣需看配对差异和不确定性，不能仅用四舍五入后的通过率判断。

所有语义错误保留，不为提高分数补跑。接口失败单列，不混成记忆能力差异。发现规则误判时保存另行解释，保留冻结原分。完成后才离线审计，不与运行进程并发修改缓存。真实流程与公共 reader 分开报告，不能把共享 reader 的三阶段重复输入节省直接外推到线上。

本轮结果用于判断下一步改进；不会自动切换现有客服默认策略。
