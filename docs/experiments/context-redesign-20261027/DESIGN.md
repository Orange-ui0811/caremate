# 客服上下文重新设计与统一实验

2026-10-27。实现与实验阶段；任何效果数字以冻结运行及审计结果为准。当前服务默认 `legacy` 不自动切换。

## 设计问题

本项目是九类意图、五类处理出口的客服。通常一次只处理一个明确对象，订单和物流会变化，商品政策必须有知识证据，退款/工单必须保留独立的确认与归属校验。上下文的目标不是尽量记住全部聊天，而是用合理成本给本轮各节点提供足够的对象、关系、条件和证据。

既有实验发现：窗口可能漏掉早期事实；摘要可能漏关系、付费生成却没有进入消解节点；规则抽取的“当前订单”可能压过用户后来换对象的原话；旧客服物流答复可能被当成当前状态。四个问题不能都用“加大摘要”解决。

## 本轮候选：近期原文＋按问题回查原文＋本轮业务证据

1. **保存层**继续使用完整会话原文和完整工具回执，归属校验与消息水位限制可读范围。来源引用为会话 ID、消息 ID、字符范围和内容哈希。原始记录不因裁剪本轮输入而丢失。
2. **选择层**先保留最近完整一轮，再以当前问题对本会话旧用户原话作词面 BM25 检索；保护最强匹配，补入最近第二轮、最多三个检索命中、相邻轮和共享订单/型号的一跳关系。去重后按时间排列。无需额外 LLM 规划调用；不依赖“最开始”等特定触发词。
3. **解释层**给原句标出用户陈述/历史客服陈述与来源。更正、否定、撤回仍按原话给已有消解/意图/回答模型理解，暂不把有限正则提取的候选槽位宣称为当前权威状态。保留原话不保证模型一定理解关系，必须用最终任务检验。
4. **业务执行层**由公共 Workflow 获得最新回执。明确物流查询、唯一订单且归属通过时，先取单获得物流单号，再查物流；记录本轮消息 ID、观测时间和工具调用 ID。历史回顾和明确不查询不自动刷新。失败不能复用旧成功答复冒充本轮查得。退款、工单原有核验与确认仍独立。
5. **预算层**每个节点按职责装配；保留原文完整轮次，保护当前问题与必要证据。不能装下则记录预算失败并澄清，不静默把完整历史改成窗口，不截断半条关键证据。本轮候选不自动生成摘要；摘要是需要单独证明价值的对照组件。

这是可测试的较小候选，而不是完整语义状态图、跨会话记忆或通用 Harness。完整工具回执恢复沿用已有机制；主实验关闭模型主动回读工具，仅评估同会话确定性原文选择，不能声称验证了全部恢复能力。

## 为什么按节点分配

|节点|需要的内容|候选历史视图上限（估算 Token）|理由|
|---|---|---:|---|
|指代消解|本轮原话、相关订单/商品关系、最新更正原句、近期问答|2400|对象弄错会污染下游，保留历史证据比单一旧候选更可核对|
|意图识别|消解后的诉求、少量相关背景，仍保留原问题|1000|九分类不需要反复携带全部历史|
|查询改写/知识检索|具体型号、问题与有效限定|2400|检索目标不能被早期话题带偏；知识事实来自本轮检索|
|最终回答|本轮诉求、必要原话、本轮知识/业务证据、当前工具调用链|4200|更大的证据空间用于作答；系统提示、工具 schema 和当前回执另预留空间|

预算使用仓库已有 `cjk-heuristic-v1` 估算；这是工程起点，不是最优参数，也不是服务商 tokenizer。五组均检查完整 API 请求的 16000 估算输入上限，输出 `max_tokens=8192`。两者是应用设置，不能拿 DeepSeek 官方当前同名别名的容量冒充 Gitee 部署规格。实际费用比较使用 API 返回的输入/输出 Token。完整历史组免除小节点视图配额，仍受完整请求上限约束；它是资源参照，不叫同预算对照。

本轮没有动态放大候选预算。否则“小窗口失败、新方案多给文本后成功”不能说明检索本身有效。后续是否增加有条件扩容，需根据本轮被预算阻断的实际失败来决定。

## 五组对比

|组|历史方法|维护|可回答的问题|
|---|---|---|---|
|L：legacy|当前滑窗、滚动摘要及各节点现有截取|原来30条消息触发、留8轮的滚动摘要|改造相对现用记忆策略是否划算|
|F：full|完整原文，不悄悄截断|无|保留全部历史的成本与效果参照|
|W：window|连续近期完整原文，同节点预算|无|仅减少输入是否已经足够|
|S：window_summary|同预算窗口加可回读分段背景摘要|2400估算历史触发、保留8轮；正文最多300字符且不超过450估算Token|摘要的新增收益是否超过维护代价|
|T：task|近期原文加问题相关原文及来源|本地索引/检索，不调用摘要模型|少量相关原文是否能替代大量历史或摘要|

F/W/S/T 使用同一来源说明和原文估算器；来源的文字开销也记入预算。L 保留旧算法，不标为纯组件消融。**所有组都启用相同物流刷新规则**，因此 L 应写作“legacy记忆＋公共执行规则”；新鲜查询的收益不能算成 T 的记忆收益。

## 统一评测

正式集：6 个业务场景族×短/长2版本=12条内部合成轨迹；每条3次真实追问×5组=180轮。开发 pilot 另存，单格只生成一次，语义答错不重跑。各方法使用自己的实际上一轮答复，按 case 轮换组顺序，避免各组共享生成历史或固定整组先后。

场景覆盖早期更正、自然换对象、商品关系、多对象限制与部分撤回、对象歧义、用户/旧客服说法与本轮工具回执冲突。限制场景主要检验只读行为和不擅自写入，不证明撤回后的完整正向授权机制。长文本含多种无关售后背景；这是挑战集，不能作为真实业务分布或外部盲测。

测试走实际 LangGraph 的消解→意图→检索/业务→证据检查→回答及真实模型调用，使用隔离的合成业务/知识夹具。物流按逻辑追问轮次改变，不按某组工具调用次数改变；要求最新查询时同时检查对象、实际新调用和答复中的当前状态。模拟工具失败与外部模型接口失败分开。

主指标是逐轮任务规则通过及整条3轮完成；同时拆分对象、动作、最新证据、澄清与未授权写入。报告全样本结果；接口故障、预算阻断、格式失败单列，不把接口超时解释成记忆差。

成本账本覆盖**预置历史的记忆初始化＋3次追问全部节点＋触发维护＋重试**。预置原始客服回答是合成文本，其生成成本不计，因此不能称全会话生命周期费用。摘要不预先免费提供。输入、输出、已知缓存字段与缺失usage分别列出；缓存命中是输入子集，不再相加。成本不能仅引用最后一次消解请求。

开发预跑 v1 暴露了摘要长度契约问题：只提示“450 Token”时，12次摘要输出按本地估算为851～1787 Token，摘要被拒收后后续消息反复触发维护。完整 v1 记录保留，独立审计通过；其结果不用于证明 T 优于摘要。正式运行前，S 改用明确的正文300字符限制并保留450估算Token检查，摘要只保留业务对象、关系、更正、限制与未完成事项，忽略通用常识。超长结果不截断；同一来源区间不反复语义重试，失败后从当时完整水位起新增原文达到2400估算Token才允许再次维护。开发 v2 专门验证这项维护契约，原数据金标准和 T 算法不变。S 是这套明确的分段摘要策略，不代表所有摘要方法；L 继续保留原滚动摘要。

记录整体与短/长分层 Token、按用途调用数、端到端/首个事件延迟、摘要生成及实际装入节点情况。流程和摘要初始化时延分开。小样本单次生成不能证明统计非劣或线上泛化；减少 Token 不等于按比例减少响应时间或账单。

数据、代码、评分和配置运行前冻结并做哈希。原始输出、错误、维护记录和调用载荷全部保留；审计离线复算规则与成本。选择器关检索/去来源标签的固定前缀消融先离线测“哪些证据消失、输入减少多少”，不把它冒充模型任务通过率；需要额外模型诊断时最多12检查点×3视图=36次，另列费用。

## 依据与面试解释

[LangChain的写入/选择/压缩/隔离](https://www.langchain.com/blog/context-engineering-for-agents)支持分层职责；[Anthropic上下文实践](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)支持按任务选择最少但足够的信息；[Manus可恢复外置](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)支持原文与本次视图分开。[LongMemEval](https://arxiv.org/abs/2410.10813)和[MemoryAgentBench](https://arxiv.org/abs/2507.05257)提供更新、时间、拒答与增量交互的测试维度，不提供本项目的最佳参数或成绩。

QueryMind借鉴点是业务执行状态与历史建议分开；Harness借鉴点是整请求预算、保留工具配对、压缩后可回查和水位校验。没有移植完整运行时。详见 research-notes.md 与 workflow-inventory.md。

面试可按“业务错误→节点所需证据→预算与来源设计→同流程对照→成本及失败边界”展开。只有新审计完成后填写结果数字；若窗口或摘要组更好，就如实说明新检索组件在该工作负载下没有额外收益。
