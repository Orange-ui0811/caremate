# 客服上下文统一评测契约与设计审查

日期：2026-10-27。状态：评测设计审查，尚非新实验结果。本文基于仓库现有结果和真实 Workflow 测试夹具制定；没有新增模型调用，没有改写旧数据、评分或结果。文中规模是本轮实施建议，正式运行前以新实验 `manifest.json` 冻结的配置为准。

**本轮已选实施边界：**实际候选 T 为近期原文＋确定性词项检索相关原句与邻居＋来源标记，不维护派生候选状态，不启用摘要，不动态扩容。W/WS/T 指代、意图、检索、回答的估算配额分别为 2400/1000/2400/4200；F 不裁原文，整请求上限 16000；输出上限 8192。WS 使用既有分段摘要，2400 触发、450 目标、保留最近 8 个用户轮；L 保留原滚动摘要。下文关于状态、动态扩容及其消融是评测设计审查中的可选命题，并非本轮已经实现或验证的能力；最终方案见同目录 `DESIGN.md`。

## 1. 这次究竟要回答什么

主要问题是：**在相同客服 Workflow 和业务约束下，新上下文策略是否用更少的模型输入与维护成本完成相同的任务，哪些组件确实有必要？**

必须分开三个层次，否则会继续出现“某一组指代更好，但最终任务更差”“省掉窗口却增加维护成本”的混淆：

1. **可用系统比较**：当前记忆策略与候选系统，在同一真实 LangGraph 流程中是否满足客服需要，实际花费多少。当前旧策略保留原算法和预算，作为实际系统锚点。
2. **同预算组件比较**：统一估算器、分节点上限、模型与执行逻辑，仅改变历史选择/摘要/状态组件，解释差异来源。
3. **固定历史诊断**：给定完全相同的历史和问题，检查缺失的证据、失效状态和摘要到底如何影响输出。这个结果解释机制，不能代替连续端到端结果。

本轮不通过增加一个通用规划模型节点解决问题。测试必须走现有 coref → intent → 业务分支 → 工具/检索 → 回答流程；某组增加的模型调用需在设计和成本中显式登记。

## 3. 五个主比较组

|标识|方法|定位与约束|
|---|---|---|
|L|当前 legacy 记忆：原滑窗、原滚动摘要、原阶段截取|实际系统锚点；保留原估算器和策略，不称同预算消融|
|F|完整原文历史|非压缩基线；必须记录实际完整请求是否装得下，不称理论效果上界|
|W|同预算原文滑窗|纯窗口基线；使用与候选相同的估算器、分节点预算、完整消息/轮次裁剪规则；不使用摘要和派生状态|
|S|同预算原文滑窗＋摘要|与 W 的区别仅为摘要及其占用的预算、维护；不额外加入来源状态和历史检索|
|N|新任务证据策略|按节点选择近期原文、任务状态与相关原句；来源/冲突检查；必要时回查或在允许额度内扩容；摘要按已声明条件启用|

所有组共用同一个模型/厂商/思考开关/温度、业务提示、工具 schema、检索夹具、权限和实时查询规则。若发现明确最新查询需要由公共 Workflow 修复，五组必须共用该修复；L 应明确写成 **legacy 记忆＋公共执行修复**，不能假称原封不动的线上系统。

同理，若给所有组增加来源展示、禁止陈旧物流或结构化输出修复，这属于共享执行条件。其收益不能记在 N 的记忆算法名下。不要只给 N 增强执行保障、然后将与 L 的差距全部解释成记忆收益。

### 预算的公平条件

正式 manifest 逐节点登记：历史投影预算、包含系统提示/工具 schema/当前证据的整请求输入上限、输出预留、摘要触发阈值及目标、检索上限、扩容条件与最大值。

- W/S/N 使用同一估算器；相同上限不等于实际用了相同 API Token，需同时报告实际用量。
- N 若允许从小视图扩容，W/S 必须有可解释的预算基线。主表可比较相同最大预算下的实际系统成本；不能故意把 W/S 限死在 N 的起始小预算，却允许 N 扩到大预算，再称等预算优胜。
- 等预算组件诊断时，各组固定相同节点上限，禁止 N 的额外扩容；摘要、状态和选中的旧原文均占用同一历史配额。
- L 是实际锚点，不因其历史估算器不同而删掉；在表中将“系统差异”与“组件差异”分列说明。
- F 的完整性要按真实发送的 payload 审计。不可静默截断 F；不可只在 F 装得下的样本里计算主表，而保留其他组全部样本。

**预检风险：**现有摘要触发约 12,000 估算 Token、整请求输入上限约 16,000；加入工具 schema、系统提示、后续回复和本轮证据后，长样本可能让 F 越界。运行前用最终 payload 做离线估算预检，预留三轮增长。若要修改上限，应对所有组一致且在冻结前完成。主比较使用所有组可运行的共同适配集；超上限压力案例单列，并保留 F 的预算失败为结果。不能既让 S 从未触发摘要，又称完成摘要收益验证。

## 4. 本轮规模与数据分层

建议主比较先做 **12 条新合成轨迹＝6 个业务场景族 × 短/长两个版本，每条 3 次追问，5 组共 180 个待评分回合**。一个场景族的短/长版本保留相同业务目标和关键关系，只调整无关历史量及关键事实距离。长版不能全部由同一句重复填充，否则只能证明压缩重复背景有效。

|场景族|三轮需要覆盖的变化|核心金标准|
|---|---|---|
|对象与歧义|明确对象 → 省略称呼 → 多候选无法确定|对象唯一时准确查询；不唯一时澄清，不擅自选最近订单|
|更正与关系|商品/订单/地点/保管人的关系 → 非模板措辞更正 → 通过关系追问|保留正确关系及最新更正；旧派生状态不得覆盖新原话|
|范围限制与撤回|两个对象分别禁止退款/工单 → 仅撤回其中一项 → 只读查询或模糊动作请求|限制的对象、动作、状态准确；撤回限制不等于授权写入|
|实时业务状态|首次物流查询 → 状态发生变化 → 要求再查/最新|本轮查正确对象，使用当前版本回执，不复述旧回执冒充新查询|
|证据冲突与来源|用户自述/旧工具结果/当前业务结果不一致 → 核实 → 追问|业务事实按来源和时效处理；用户诉求仍作为诉求；不把推断当工具确认|
|知识与拒答边界|已知商品规则 → 近似但缺证据的问题 → 回到先前商品或增加限制|检索目标、证据充分性、澄清/拒答和最终答案一致，不用摘要填造缺失政策|

长度分层要按**完整发送前的历史估算**记录，同时保存消息数、轮数、关键证据到问题的距离、实体数量和冲突数量。不要用“24 轮”代替容量描述。一段长工具输出与 24 个简短问候的压力完全不同。

为控制本轮调用量：

1. 开发 pilot 最多 2 条轨迹、每条 3 轮；发现 harness 或评分错误可改，但 pilot 结果不进入正式表。
2. 正式五组每个格子只跑一次，不因某一组答错再生成“更好的一次”。温度为零也不能宣称完全确定。
3. 主比较上限 180 轮。诊断模型调用另设最多 12 个固定历史检查点，每点最多 3 个版本，共 36 次调用；只有主比较触发预声明机制问题时才运行。
4. 若本轮能力和时间不足完成消融，报告“主比较已完成，组件必要性尚未证实”，不要扩大主实验或用叙述补出收益。

这批数据是**新冻结的内部合成验证集**，不是独立外部盲测，也不代表真实客服流量比例。若所有新案例都只针对已知失败设计，应明确为挑战集；可用于筛方案和解释失败，不能直接给线上通过率承诺。短/长同族并非 12 个完全独立任务，统计时要保留族级相关性。

## 5. 冻结、试验执行和复现

冻结顺序：完成 pilot → 修复公共 harness/评分 → 冻结新数据及期望状态 → 冻结五组配置、源代码与提示 → 执行主比较。算法在正式结果出来后调整就产生新版本，不能覆盖本次记录或沿用同一个测试集称新盲测。

冻结产物至少包含：

- 数据/代码/提示/工具 schema/配置 SHA-256，必要依赖和版本。
- 模型名、厂商、思考模式、温度、结构化输出模式；不保存密钥。
- 每条历史消息和工具回执的标识、时间/版本、归属、来源校验值；金标准不传入模型或历史选择器。
- 摘要初始化与维护调度、预算与溢出行为、模型格式重试规则、传输重试规则。
- 模型调用池并发、优先级、超时、缓存和实验顺序；价格如需折算金额，独立冻结有效来源与计费日期。

在同一 case 内轮换不同 arm 的运行顺序，以减轻“全跑 A 再全跑 B”的接口负载和缓存时段偏差。轨迹内部必须按追问顺序运行，并保存真实上一轮回答；不能用统一的理想回答替换失误后的历史。每个 arm/case 独立数据库夹具、摘要、状态、工具回执和图检查点。

旧 harness 使用全局 monkeypatch；同进程中不能并发运行不同 arm。若要并发，必须进程隔离且各自独立输出与数据库，不共享写缓存。可先串行，成本和可审计性比跑得快更重要。

### 动态工具夹具

物流、订单状态等按**固定的业务逻辑时钟**变化，例如追问 1 返回 `event_v1`，追问 2 返回 `event_v2`；不能按某组调用次数变化，否则多查一次的策略获得了不同世界。

工具输出包括对象、观测时间、版本、状态和来源。评分要求确需新查询时，本轮存在目标工具调用且最终事实与该回执版本一致。静态字面值不够：应设计旧值和新值互斥、不会同时正确的反事实版本，例如“已揽收/派送中”或不同预计时间。

工具失败也要可复现：固定某个逻辑回合返回可识别失败；正确行为是说明未取得最新状态、适当重试或澄清，不可把旧成功记录当作本轮成功。业务工具失败与外部模型 HTTP 故障是不同维度。

正向写入授权不在本轮只读主测中声称覆盖。旧 runner 遇 `confirm_ticket` 一律拒绝；因此只能验证没有越权执行。若测试撤回后的真正写入，需另建隔离写夹具和明确确认事件，并同时验证确认的用户、对象、动作、版本与有效期；“取消禁止”从来不是“已经同意执行”。

## 6. 两类互补实验

### A. 连续真实 Workflow 主比较

预置历史包含脚本化原话和工具材料；三轮追问调用真实模型和实际流程，每轮输出进入后续历史。该结果同时包含信息选择、改写、分流、工具使用、随机生成及后续轨迹变化，适合回答“这套系统实际怎样”。

初始化记忆必须有成本：按已冻结的生产维护检查协议，将历史按时间顺序进入各组，调用该组需要的摘要或状态提取，保存触发/未触发记录。若为了省钱改为在检查点一次性构建历史记忆，要对所有组明确采用同一初始化口径，并说明它不是完整在线生命周期。**不得给 S/N 预先塞入免费摘要，却让其他组承担全部调用。**

此工作负载应命名为“预置历史的记忆准备＋三次真实追问＋触发的维护”，不叫完整会话成本；预置历史原始客服答案的生成成本未测。要评估完整在线生命周期，需要另做从第一轮开始实际生成的轨迹。

### B. 固定历史、同预算诊断

选择器与记忆层离线先验证全部检查点：关键原句是否可见、来源能否回读、状态更新是否正确、是否使用未来消息、预算是否真实满足。固定历史诊断统一历史、问题、reader 和工具材料；不继承各组前轮不同的生成结果。

最小消融按待证明命题单独进行：

|待证明命题|有效诊断|不能证明的比较|
|摘要恢复了窗口外信息|W vs S，相同固定历史/预算，旧证据确在窗外；检查摘要提到正确关系、实际装入依赖节点并改善输出，计入维护|未触发摘要；只比较“有摘要字段”；用已含关键证据的大窗口与小窗口比|
|来源状态有净收益|N vs N 去状态，保持原文选择和预算一致；更正/撤回案例中检查状态字段与输出，包含旧状态误导的反例|同时移除状态和检索；给状态组更多 Token；仅凭日志含 source_id|
|按需回查有必要|N vs N 禁用回查，其他包相同；关键原句确在近期窗外且没有已被摘要完整保存，记录命中、装入和使用|N 与 W 的全面系统差；只统计检索召回，没有看最终对象和动作|
|来源引用改善冲突处理|相同事实文本，带/不带来源身份和时间，构造用户陈述与新业务回执冲突|简单记住订单号；把引用字段存在称作因果收益|
|小视图可节省简单请求成本|已明确目标、无远端依赖样本，N 小视图与较大固定视图完成同任务且计入所有调用|仅压力集总体省 Token；把少回答/安全但无必要澄清当成等效成功|

移除某组件后释放的空间是否由原文填充必须预先规定。建议同时区分“保持其他输入完全不变的删除诊断”与“同预算重新装配的替代策略”：前者解释该片段作用，后者衡量该配额是否值得分给它。不能把两种效应混称同一个消融。

36 次诊断调用上限不能承载全部表格组合。本轮优先用离线证据覆盖与状态断言检查所有组件；若正式结果暴露某一机制，再按预定顺序验证不超过两个命题。未运行的命题明确保留为未验证。

## 7. 评分契约

主分数仍以每轮任务是否完成计数，但必须拆出可复算的组成项。推荐 `task_pass = completed ∧ target_ok ∧ action_ok ∧ evidence_ok ∧ freshness_ok ∧ boundary_ok ∧ answer_ok`，不适用项在数据中显式标记，而不是默认为通过。

|评分维度|独立真值/核验对象|
|---|---|
|对象与关系|数据作者预定义的对象、可接受候选集合和关系；对象不唯一时允许的澄清集合|
|动作与工具|本轮应执行/可执行/禁止的动作；必要工具的名称、目标、结果版本；额外只读查询单列成本，不机械等同任务失败|
|限制更新|对象 × 动作 × 生效状态 × 来源的期望转移；复合句和部分撤回逐字段检查|
|信息来源|用户陈述、系统确认、模型假设分别存放；原话与回执引用能否按归属和时间回读|
|事实与实时性|最终回答采用的业务事实与本轮权威回执一致；未取得实时回执时不能声称查到了最新情况|
|知识证据|正确知识对象/政策，以及关键条款、限定条件和证据不足时的处理|
|回答有效性|完成用户当前请求；正确澄清可通过、逃避明确可答任务不能靠“安全”通过|
|边界|无错对象写操作、无缺授权执行、无跨用户读取、无将历史限制撤回解释为新授权|

不要以“答案包含订单号/断电/软布几个词”替代整体语义；也不要把安全的额外询问、同义表述误判成错误断言。可确定的对象、状态、工具与授权项应由规则和夹具真值评分；开放文本答案按冻结的语义 rubric 复核。模型辅助复核只作第二层诊断，标注“模型辅助”，不称独立人工标注。

保留原始规则分和复核意见分栏。若正式评分器确实有 bug，发布修正版本并同时重算**全部组全部条目**，保留旧版，披露变化；禁止只修改输掉的一组或失败条目的规则。

除回合通过率外，报告三轮全部成功的轨迹数、每个场景族通过率、关键边界违规数、澄清率与不必要澄清率、工具新鲜度、状态转移正确率。连续轨迹后续的失误可以是前轮传播所致，需显示最早分叉点。

## 8. Token 与延迟全账

主成本为所有实际提交给供应商的请求 input＋output Token，包含：指代、意图、检索改写、证据检查、Agent 工具循环、最终回复、摘要、模型式状态提取/检索规划、格式重试以及有回执的传输重试。后台维护同样计费。

记录 `arm/case/turn/stage/request/attempt` 唯一归属；主表分输入、输出、维护、重试、总量。缓存读取是输入的子集，不再次相加；本地结果回放不伪装新模型调用。提供 usage 的失败照计；没有 usage 的请求标为未知成本，不记成零。

向量化、重排、数据库检索若使用真实服务，另列服务用量/费用；不能把异构供应商 Token 简单相加成同一种价格。使用本地或静态夹具则明确没有测这些外部成本。未核实计价时报告 Token，不给似乎精确的人民币。

同时提供：每条轨迹总 Token、每个成功回合的总体成本（分子包含失败消耗）、简单/压力分层、各阶段分布、额外工具调用数。不要只在“所有方法都成功”的子集中计算成本作为主结论，这会筛掉最昂贵和最难的失败。

延迟分别记录用户可见首次 SSE、前台完成、后台维护完成以及总模型服务时间。测试为等维护完成加的 barrier 不是生产前台延迟；不能把它混入前台后称用户实际等待。报告 P50/P95 时保留样本数和失败超时，单次小样本 P95 只作描述；Token 减少不等于延迟必降。

## 9. 失败、继续与结论阈值

模型 HTTP 超时/限流/连接失败、结构化协议失败、预算溢出、业务工具失败、语义答错分别记录。SDK 原有格式/传输重试必须所有组一致且计账。除预声明的传输故障恢复外，不为语义答错、模型不肯调用工具或格式错误补跑来改善结果。

发生外部接口故障时先保留初始阶段，恢复时只重试相同冻结合同的未完成传输项，保存首次与恢复成本。连续轨迹断在中间，后续标记依赖阻断；不可偷偷用理想历史续跑，也不能删掉整条轨迹后仅报剩余成功分母。模型/供应商/预算改变需要新传输或实验阶段，不能合并成完全相同条件。

本轮 12 条轨迹、6 个相关场景族无法可靠证明“普遍非劣”或排除 5 个百分点的退化。建议预先声明工程筛选标准：

1. 关键安全边界不允许新增违规；仍需独立测试，不由小样本零违规推断风险为零。
2. 对比实际锚点和预算基线，列出每个配对新增失败、修复失败及轨迹影响；旧共同缺陷不能抵消新关键失败。
3. 以总 Token 节省为实际目标，例如 20% 可作为目标值，但不能事后改变参考组来达到目标。
4. 分数持平但样本小，只能说“本轮未观察到新增任务失败”；分数下降要给出减少多少成本、失去哪些能力，不能写“无损”。
5. 有配对区间时按场景族重采样并标为描述性；不以区间包含 0 或 p>0.05 作为非劣证明。若需要正式非劣结论，应根据预计配对差异、聚类和预声明界值另做样本量规划。

最后以效果—成本前沿选方案，而不是仅挑最高通过率或最低 Token。若 N 没有证明状态/回查相对 S 的收益，应优先保留更简单且可靠的实现，或仅在明确触发场景启用组件。简历表述只能使用本次实际测试规模、工作负载和结果；不能把计划目标写成取得的提升。

## 10. 实施前后的审计清单

运行前：五组实际 payload 和预算预检；动态夹具版本对齐；评分真值独立；旧缺陷回归通过；所有成本入口有记录；pilot 与正式目录分离；源码/数据/提示冻结。

运行后：180 个计划回合是否都有成功、失败或阻断状态；每条轨迹真实输出是否进入下一轮；调用、attempt、维护与 usage 是否一一归属；有无未知成本；F 是否完整；摘要是否触发并被依赖节点看到；状态与原话是否冲突；动态业务结果是否按固定时钟变化；离线重算评分和总账是否一致。

审计不能仅检查报告文件存在。必须检查所有预定格子的记录、源码/数据快照、逐条评分、维护记录以及工具/状态版本。原始结果只追加审计和解释，不原地修饰。

## 11. 对新设计的独立质疑

- 结构化状态不是天然可靠的“真相”：旧规则已经把复合撤回读错。若 N 没有可检测冲突与回到原文的路径，状态可能比不加状态更差。
- 留下来源位置只是可追溯基础；只有能在权限和预算内读回、并对冲突作正确处理，才形成实际收益。
- “按问题相关性选择原句”可能选到两个实体却漏掉关系或更正。评测应以关系链和限定条件为证据单位，而不仅是实体命中。
- 摘要会消耗空间和维护费用，并可能永久丢失否定、作用域、时间和关系。若原文窗口已够用，默认摘要可能没有净收益。
- 更大的模型窗口只是容量许可，不是每轮填满的理由；也不能仅凭模型名称归因所有结果。模型与预算、任务长度、证据位置、工具流程共同决定效果。
- 通过提示词让 Agent 记得查最新物流，不如显式 Workflow 契约可验证；但这一工程修复与上下文算法是两项工作，应分别说明。
- 12 条挑战轨迹只能帮助选下一版，无法成为全面线上收益证明。可解释的失败和完整成本账，比夸大的单一准确率更适合面试展开。
