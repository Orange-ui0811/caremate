# 新统一评测的数据与评分契约

冻结前版本：`context-unified-cases-20261027-v1`。源码为 [context_unified_cases.py](E:/Mewhelp/scripts/context_unified_cases.py)，离线完整性与反例测试为 [test_context_unified_cases.py](E:/Mewhelp/tests/test_context_unified_cases.py)。

## 数据

`dataset()` 返回 12 条会话：6 个业务族各配一条短历史、一条长历史，每条 3 次连续追问，共 36 个评分点/方法。短/长配对的关键事实和追问一致，只改变干扰历史长度。六族分别为早期订单更正、自然任务切换、位置-商品-部件关系、只读条件下的部分限制撤回、多候选对象澄清、工具事实权威与新鲜度。

这是一套内部预先编写并冻结的合成回归数据，设计者知道题型；不是独立第三方盲测或真实客户抽样。12 条也不是 12 个完全独立业务分布，统计时应按会话或业务族聚合，不把同一会话的 3 轮假装独立。

`pilot_dataset()` 另有 2 条冒烟测试会话，不计正式分数。每个 case 含 `id/family/stratum/initial_history/steps`；每个 step 含 `query/expected`。**模型只能接收历史、query 和实际 fixture 返回，不能接收 expected、purpose 或评分代码。** 后续历史使用该方法实际生成的回答，不用金标准回答替换。

其中 `pilot_cleaning` 预置约 3100 估算 Token、至少 30 条消息的通用资料背景，专门验证摘要初始化、维护记账和后续可见性；另一条物流 pilot 验证动态工具结果。pilot 仍不进入正式分母。

历史长度采用项目公开的估算公式：中文字符×1.2，其他字符/3，再加包装常数；仅用于规划，正式成本取供应商 usage。目标短历史约 600～900、长历史 7000～8000 估算 Token，长历史混合多类通用客服资料问题，仍属人工干扰而非自然长会话。正式 runner 必须验证最终系统指令、工具 schema、历史、当前问题与保留输出预算；不能从初始历史小于 8000 推导最终请求一定小于 16000。

商品清洁事实复用当前真实 Workflow 评测已有的三项合成夹具（MH-FD10、MH-CAM1、MH-LP100），`PRODUCTS` 提供唯一文本来源；`ORDER_PRODUCTS` 提供固定合成订单关系。没有访问实际客户库。初始化历史的生成成本未测，因此总成本口径应为“初始化维护与三次后续请求及其维护”，不能称整个历史从第一轮生成的成本。

## 动态物流夹具

真实 `query_order(order_id)` schema 返回 `tracking_no`，随后 `query_logistics(tracking_no)` 读取物流。runner 必须记录由运单解析得到的 `resolved_order_id`，不能为了评分把工具签名改成直接接订单号。

每轮可见自然状态由 `logistics_event(turn)` 决定：第一轮离开杭州分拨中心，第二轮到达宁波中转站，第三轮交由鄞州网点派送。还可附 `version=物流记录N` 供审计。所有方法在相同轮次读取完全相同的夹具。模型不用背诵版本编号，但必须回答本轮自然状态；只出现版本编号不算回答完成。

预先声明的例外：`tool_authority_freshness` 的短/长两条会话第三轮，物流服务固定返回业务错误。fixture 不应在这个错误回执中同时返回最新状态或版本。该轮要求实际尝试正确订单并如实说明本次未能核实，允许有明确时间限定的历史回顾；不得把旧状态当作当前成功查询结果。它仍在36轮主分母中，属于预设业务任务，不是模型供应商接口故障。

## score_turn(record) 接口

输入为真实 Workflow 保存的记录：

```text
coords: {arm, case_id, turn: 从1开始}
query, expected, answer, state, status, error
executed_tools: [{name, args, result, resolved_order_id, coords}]
proposed_tools: [{name, args, coords}]
retrieval: [{query, requested_skus, returned_ids, coords}]
```

输出含 `checks`、`task_rule_pass`、`transport_failure`、口径说明。`task_rule_pass` 为本轮适用检查的逻辑与，所有方法运行相同代码，评分不读取 arm 名。

| 任务 | 必须同时满足 |
| --- | --- |
| 所有任务 | 流程完成、上下文未报 memory_error、有回答、无写操作提议或执行；存在终止错误则失败 |
| 物流 | 本轮实际执行目标订单的物流工具；没有读取错误订单；存在本轮成功回执；回答包含本轮自然状态 |
| 未核实旧签收说法 | 上述物流条件，且不把旧的“已签收/已送达”当作当前事实；允许明确引用并否定旧说法 |
| 物流业务失败 | 实际尝试正确对象并观察到业务错误；说明失败或无法核实；不编造当前物流成功状态；不将旧签收结论当作事实 |
| 商品清洁 | 本轮检索对应型号且不检索别的型号；回答包含该问题预先声明的事实词组；不读取订单 |
| 对象不明 | 查询前要求用户明确对象；不读取任一候选订单；不编造夹具物流进展 |

澄清可以出现两个候选订单号，也可以说“未查询另一张单”；不会把单纯提及号码判成幻觉。物流主要检查实际工具参数，不依赖“回答有没有打印订单号”。

这些是透明、可离线复算的**任务规则通过率**，不是人工语义准确率。词组规则允许列出的自然改写，但仍可能漏掉未列出的同义句，也不能发现所有复杂矛盾；应对失败、方法分歧和安全相关输出保留人工复核，复核结果与冻结规则分数分列，不能看正式结果改规则提高得分。

局部限制撤回族的 `active_constraints` 是独立状态审计标签，未加入本轮任务主分数。其只读查询可检查目标和无写行为，不能证明撤回后的写授权逻辑正确；后者需独立执行器测试。报告必须保留这项限制。

接口超时/网络故障（包括运行器的 `interface_error`）留在主分母，并用 `transport_failure` 单独标记。前轮失败导致后轮根本没有发请求时，标记 `dependency_blocked`；两者统一计入 `infrastructure_failure`，但不能把后轮阻断算成新一次 API 失败。成功子集可补充描述，但不能替代全样本结果或被解释为上下文能力。评分单测包括旧答案配新工具、只有旧轮工具、错误订单、只有版本号、未执行写提议、允许候选号码、错误商品、预设业务错误、终止超时和依赖阻断，防止这些错误被规则误放。

`state.memory_error` 或明确预算异常另记 `budget_failure`，也计入基础设施失败；即使运行器恢复为澄清回答并将外层状态记为 completed，也不能通过上下文就绪检查。被生产 fallback 吸收的内部意图/消解接口错误需由 runner 的逐调用记录另行诊断，纯 score_turn 无法仅从成功回答推断它们发生过，报告应同时保留调用失败数与回合规则结果。
