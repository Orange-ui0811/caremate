## 约 60 秒口述

> 多轮客服有两个矛盾：全量历史越来越贵，只留最近窗口又会忘记很早的订单和型号。项目保留近期原文，把更早的对话滚动压成摘要，并用摘要加最近消息把“它”“最开始那个订单”补成完整问题，再做意图识别。摘要在一轮结束后后台生成，成功后同时更新摘要和消息边界，失败就保留旧状态。已有实验把完整历史、仅滑窗、摘要加滑窗放在同一批 24 条合成长对话上比较：末次追问规则通过分别是 23、6、21 条。摘要方案比仅滑窗保留了更多早期信息，但仍比完整历史差两条。输入 Token 的下降只针对最后一次指代请求，摘要维护另计，所以我不会把它称作全会话成本下降。

## 当前实现需要讲清的四件事

1. **数据库与模型上下文不同。** 完整消息仍可保留在会话状态/数据库；发送给模型前才组装摘要和窗口，并非把旧聊天从数据库删掉。
2. **摘要边界按消息 id 对齐。** 新增消息达到默认 30 条时尝试摘要；保留最近默认 8 个用户轮次的原文，将更早的新滑出段与旧摘要一起重写。窗口还受 3000 个近似 Token 的裁剪约束。
3. **指代模块并不读取完整的 Agent 窗口。** `_history_text` 在窗口基础上再取最近 **6 条消息**，加上摘要前缀。参数名 `max_turns` 容易误导，但代码切的是消息列表；不是六个完整用户/客服轮次。
4. **摘要有损且异步。** 生成失败不覆盖旧摘要和边界，下次满足条件时再触发；后台未完成时，下一轮可能仍用旧摘要。进程内 `_running` 防重复，不等于跨进程持久任务队列。指代模型失败则回落用户原句，保障流程可继续但不保证语义已补全。

当前主 Agent 将摘要与本轮证据放在用户侧材料消息中，固定系统提示保持不变；[nodes._agent_messages](../../app/graph/nodes.py#L271) 的实际组装应优先于早期设计文档。不要照旧文档说“摘要永远是第二条 SystemMessage”。

### 如何解释当天实际出现的追问失败

2026-10-23 的两个主服务 `/api/chat` 请求均正常结束，没有接口错误。第一轮总耗时 **37.98 秒**、首字 **33.36 秒**、返回 **10 条引用**；第二轮等待 **113.07 秒**后固定拒答、返回 **0 条引用**。它们在独立合成会话中运行，会话随后软删除，原始记录见上表链接。

第二轮状态中的 `resolved_query` 为 `智能猫砂盆 Pro(MH-LP100) 支持 App 远程监控吗？`，说明本次指代改写成功。意图识别为商品咨询，四信号分数 **0.2698** 已高于 **0.26** 阈值；`fallback_source=self_check` 说明实际停止在证据充分性检查，不能把最终拒答归因于没有记住型号。

可以这样讲：“我先检查每一层的中间结果。这条追问的型号已经补对，说明上下文在指代阶段起了作用；但下游自评拒绝生成，所以完整客服任务没有完成。这也是我将实验的指代规则通过率与端到端客服成功率分开的原因。”

还有一个从源码确认的问题：[retrieve_knowledge](../../app/graph/nodes.py#L180) 使用原始用户句子 `_user_text(state)` 作为问题理解输入，没有优先使用已经生成的 `resolved_query`。这让知识检索无法直接复用上游补全结果。但**尚不能证明它就是本次拒答的唯一或确定原因**；需要用相同状态对照两种查询，检查召回原文、自评输入与模型输出。保存的自评理由仅为“问题中”，不能凭这段不完整理由推断更多。当前仅记录问题，没有改生产代码或宣称修复。

若希望再演示订单路径，可提前验收 `查询订单1001的物流。` → `它现在到哪里了？`，并查看补全后的订单号；本次没有执行这组请求，不把它列为已通过样例。长历史结果继续以固定实验归档展示，避免把一次近期指代成功说成已经验证滚动摘要。

## 实验到底测了什么

权威文件为 20261016-v1/audited_report.json（本机归档 `data/ch07/context-eval/20261016-v1/audited_report.json`，未随源码发布），配套 REPORT.txt（本机归档 `data/ch07/context-eval/20261016-v1/REPORT.txt`，未随源码发布）、manifest.json（本机归档 `data/ch07/context-eval/20261016-v1/manifest.json`，未随源码发布）、24 份 `ctx-*.json` 与 source_snapshot（本机归档 `data/ch07/context-eval/20261016-v1/source_snapshot`，未随源码发布）。

数据是 **24 条合成文本对话**，四类各六条：早期订单追问、早期商品追问、订单号更正、近期话题切换；轮数为 24/32/40/48/56/64。每种策略每条只采样一次，在末尾做一次指代改写。模型为 `deepseek-ai/DeepSeek-V4-Flash`，摘要/指代温度 0.3，摘要触发 30 条消息，原文保留 8 轮、近似窗口预算 3000 Token，指代近期上限 6 条消息。

|策略|严格规则通过|末次指代 API 输入 Token 总和|每条平均输入 Token|
|---|---:|---:|---:|
|完整历史|23/24，95.8%|277,943|11,581.0|
|仅滑窗|6/24，25.0%|26,302|1,095.9|
|摘要+滑窗|21/24，87.5%|29,926|1,246.9|

“规则通过”要求目标实体和意图关键词保留、没有干扰实体，并经严格审计排除编造编号和错误商品身份。它是规则评分，不是人工语义准确率，也没有运行完整 LangGraph 客服任务来衡量最终业务完成率。最初规则误通过过一条“正确 SKU 加编造订单号”的输出；严格审计统一重判全部策略后，保留审计前后产物。

摘要策略还发生 **112 次维护调用，输入 257,387 Token，输出 20,134 Token**。把全部摘要预处理与末次指代输入合计为 287,313，相比完整历史末次指代的 277,943 高约 3.37%。这也不是全会话总成本：早先每轮的指代和 Agent 调用没有完整测量。因此这组数据能证明的是最终请求长度下降与早期信息保留的取舍，不能证明整体成本降低。

实验中等待摘要完成后再测试，线上则异步执行；不能把实验耗时等同于在线响应时延。24 条模板化样本和单次采样也无法证明对真实用户语言的泛化。

## 常见追问及答题要点

1. **为什么不直接把全部历史给大窗口模型？** 能作为准确率基线，但输入长度、延迟、缓存和费用会变化；现有实验完整历史准确率仍最高，所以不要声称摘要全面胜出。按工作负载算包括维护在内的成本后才能决定取舍。
2. **摘要里已经有订单号，为什么还会错？** 实体出现不等于关系正确；型号归属、订单更正、当前话题切换可能失真。报告的实体覆盖率不能代替指代规则通过率，更不能代替业务成功率。
3. **为什么不是整个会话省了 89%？** 11,581→1,247 只统计最后一次指代 API 的输入。112 次摘要维护及早期轮次没有采用同样完整账本，必须分开解释。
4. **摘要失败或用户连续追问怎么办？** 保留旧摘要和边界，窗口继续工作；后台完成后后续请求才读取新摘要，失败时下轮再触发。需要关注摘要滞后、并发顺序及跨进程任务治理。
5. **怎样迁移到工业排障？** 把设备型号、故障时间、已做检查、参数变更和约束作为必须保留的事实；保留来源与更正关系。可研究结构化状态加原始记录检索，但当前生产实现是文本摘要，不能把这个改进方向说成已经实现的工业诊断能力。
