# 知识反馈与主题分类：面试证据与演示

> 发布说明：本页保留历史实验的口径说明；本机会话、运行记录及评估产物未包含在公开源码中，相关数值不能仅凭本仓库独立复核。可用所附测试数据与评估脚本重新生成报告。

核对日期：2026-10-23。以下以当前代码、落盘报告和本地接口为准。讲解项目能力时，个人贡献另按真实经历说明。

## 这条简历应该怎么改

当前代码支持反馈收集、标准化归并、主题分类和人工审核写回；**当前可展示的分类指标是 149 条测试样本、micro-F1 93.66%，不是 161 条、96.4%**。

可以替换为：

> **知识反馈与更新：**利用 MySQL 收集检索低置信度、生成前证据自评不足及用户未解决反馈，保留召回快照，经标准化和查重归并形成待审知识缺口；构建 RoBERTa 17 类多标签主题分类流程，完成语料清洗、验证集阈值扫描及 ONNX 部署，在以合成语料为主的 149 条留出测试集上 micro-F1 为 93.7%，辅助人工确定补库优先级，并在审核后写回知识库。

| 原表述 | 当前证据和边界 |
|---|---|
| “低置信度、自评不足及用户未解决的问题入库” | 成立。自评指的是**生成前证据是否够回答**，不是生成后给答案打分；点赞只记录日志。 |
| “保留召回快照” | 成立，但不是每个反馈都有快照。检索路径保存 Top3 原文、重排分和章节；用户点踩尽力回捞最近一轮，问题对得上才用。 |
| “标准化、查重归并” | 成立，是后台批处理；模型与最多 200 条近期候选匹配，不是全库无限规模语义去重。 |
| “17 类多标签分类” | 成立，是知识反馈的**旁路主题统计**，与在线九类意图分流是不同任务。 |
| “161 条、micro-F1 96.4%” | 当前报告与当前页面均不支持。若确有旧实验，需附对应数据集、模型、阈值和旧报告，单列为历史结果，不能配当前 Demo 直接展示。 |
| “辅助人工审核写回、提升系统完备性” | 有人工审核写回链路；没有据此证明线上解决率提升或补库后收益的对照数据，宜说“形成可审核的补库闭环”。 |

## 60 秒口述

> 客服答不上来时，问题不会直接丢掉。系统把检索分数不足、生成前证据自评不足和用户点“未解决”的问题收进 MySQL，并尽量保留当时召回了什么，方便区分“库里没有”和“检索或回答出了问题”。后台批处理把原话标准化，再与待审队列查重，同一个知识缺口累计出现次数。另一个 RoBERTa 分类器给这些标准问题打 17 类主题标签，主要帮助判断优先补哪类知识，不参与在线九类意图分流。人工需要核实业务规则、修改答案草稿，通过后才写回 MySQL 和 Milvus。分类器当前留出测试集是 149 条，micro-F1 为 93.7%；这批数据主要是模拟问题，所以它证明的是当前场景里的离线效果，还需要更独立的真实问题测试。

## 投屏顺序：约 3 分钟

先在 GitHub 打开本页，保留三个标签页：`/review`、`/topics`、`/acceptance/eval`。这里的本地链接只在运行项目的电脑上有效。

### 1. 反馈如何进入待审队列（约 60 秒）

打开[飞轮待审队列](http://127.0.0.1:8000/review)。选择事前确认可以展示的演示记录，展开详情，指出标准化问题、出现次数、来源，以及原始问题对应的召回快照。

讲：“同样的诉求可以合成一个知识缺口，出现次数用于排序。召回快照可以帮助审核人判断到底是缺知识还是没检对。”然后展示“通过并写回知识库”的弹窗，指出预填的是 AI 草稿，**点击取消**。这一步足以说明人工把关，现场默认不提交知识修改。

“立即处理新问题”会调用模型并写待审记录；“确认通过”会调用嵌入并修改知识库。演示默认只展示已有记录与流程。若要演完整的“点踩→归并→补库→重新问答”，提前在独立演示数据中排练并准备核准答案，不把临场编写的政策写进正在使用的知识库。

代码证据：[反馈接口](../../app/api/feedback.py#L19)、[拒答落池](../../app/graph/nodes.py#L130)、[标准化归并](../../app/core/flywheel.py#L38)、[人工审核写回](../../app/api/review.py#L72)。

### 2. 为什么还需要分类器（约 30 秒）

打开[主题分布](http://127.0.0.1:8000/topics)，说明这是已归类问题按主题的分布。多标签问题会计入多个主题，柱子的数量相加可以大于问题总数。

讲：“九类意图决定这一轮客服怎么走；17 类主题决定积累下来的知识缺口先补哪一类。后者是旁路批处理，不增加每一轮客服的分类耗时。”如需展开样例，提前确认展示内容适合公开。

代码证据：[只分类已归并问题](../../app/db/repository.py#L610)、[旁路分类脚本](../../scripts/ch10/classify_pool.py#L29)、[分布聚合](../../app/db/repository.py#L635)。

### 3. 分类效果与局限（约 90 秒）

打开[分类器验收总览](http://127.0.0.1:8000/acceptance)，再进入[评测与阈值](http://127.0.0.1:8000/acceptance/eval)。先指明样本数、micro-F1 和阈值，再往下找到“单句试分类”。

2026-10-23 用本地 ONNX 服务实测以下公开构造的例句：

| 输入 | 当前输出 | 用来说明什么 |
|---|---|---|
| `快递到哪了` | 物流 | 单标签情况。 |
| `没有合适的尺码，想退货` | 退换货、尺码 | 一句话可以命中多个标签，各标签独立过线。 |
| `猫窝买大了想退，退回运费谁承担？` | 退换货、运费 | 这个表达漏掉了尺码诉求，可主动展示当前分类边界，不必包装成全部正确。 |

单句试分类只调用本机 `:8110` 的 ONNX 模型，不调用付费聊天模型、不写知识库。本次核验该服务健康检查返回 200，上述样例成功返回。线上主服务的验收接口也展示相同的 149 条、93.66% 指标。

最后打开[错例复核](http://127.0.0.1:8000/acceptance/errors)，讲一类错误及可能改进方向。默认不点击重跑训练、重新造数或重新导出；这些操作无需现场等待，也可能覆盖展示用报告。

## 面试中必须说清的数据口径

当前评测报告（本机归档 `data/ch10/reports/eval_report.json`，未随源码发布）生成于 2026-10-11：

| 项目 | 当前值 |
|---|---:|
| 测试集问题数 | 149 |
| micro precision / recall / F1 | 94.97% / 92.39% / 93.66% |
| macro-F1 | 93.12% |
| 使用阈值 | 0.45 |
| 验证集问题数 | 149 |
| 验证集阈值扫描最优 micro-F1 | 94.25% |
| ONNX 与 PyTorch 校验条数 / 标签不一致条数 | 149 / 0 |

micro-F1 汇总所有标签上的 TP、FP、FN 后计算，不等于“149 句话中有 93.7% 的标签集合完全正确”。当前报告总 FP 为 9、总 FN 为 14。物流、尺码、质量问题三类未通过项目设定的严格类 F1 ≥ 0.9 红线，不能只展示平均分并声称所有类都达标。

核对当前文件得到的数据血缘：

- 原问题池快照 17 条，清洗后 10 条；标注语料总量 1,469 条，其中来源标记为 `pool` 的 10 条、`simulated` 的 1,459 条。`pool` 只表示来自本地问题池，不能据此称为真实线上客户数据。
- 训练文件 2,367 条，其中精确唯一文本 2,365 条；验证和测试各 149 条。训练集包含增强和定向补充，所以最终不是简单的 80/10/10 文件条数比例。
- 对照标注语料的来源字段，当前验证集 149 条全部来自模拟语料，测试集是 148 条模拟语料加 1 条问题池语料。
- 三个划分之间精确文本交集为 0，但这不能证明近义改写、相似模板或相同生成来源之间没有泄漏。训练文件内部仍有两条重复计数，需要继续治理。

因此更准确的结论是“在当前主要由合成问题组成的留出集上有效”，不应推导成生产问题上的 93.7%，更不能推导成真实客服解决率。针对错误补训练语料之后继续查看同一份测试集，也会削弱最终测试集的独立性；后续应另建从未用于调试的冻结测试集。

## 最容易被追问的八个问题

**1. 为什么用多标签，为什么不用 softmax？**

“尺码不合适想退货”同时涉及两个主题。训练时用 17 维 multi-hot 标签和 `multi_label_classification`，各标签使用 sigmoid，损失为 BCEWithLogitsLoss。softmax 通常用于互斥单标签任务，各类概率和为 1，不符合这里的多个诉求同时成立。源码：[编码和训练](../../scripts/ch10/train.py#L24)。

**2. 17 类怎么定义，和九类意图有何关系？**

17 类及边界来自[统一主题表](../../app/core/taxonomy.py)，用于分析知识缺口；九类意图用于在线路由。不要说 RoBERTa 在做在线九类分流，也不要把这两个分类任务当作同一个评测。

**3. 数据怎样划分，增强会不会把测试题混进去？**

先按标签组合分层、固定随机种子划分；小组合归入其最小 label id 对应的层，极小层只进入训练。然后只增强训练集，并过滤与原语料完全相同的变体。[划分逻辑](../../scripts/ch10/corpus_lib.py#L33)、[增强与定向补充](../../scripts/ch10/build_dataset.py#L66)。目前是精确文本层面的隔离，仍需要近重复聚类、模板或来源分组后的划分验证。

**4. 为什么选 0.45，是否在测试集上调参？**

训练完成后在验证集扫描 0.30～0.70、步长 0.05，选 micro-F1 最优的全局阈值，保存到 `threshold.json`；测试集使用已选阈值。当前扫描报告（本机归档 `data/ch10/reports/threshold_scan.json`，未随源码发布）为 0.45。此分类阈值与 RAG 证据置信度阈值完全不同。源码：[训练扫描](../../scripts/ch10/train.py#L98)。

还要知道实现细节：训练扫描直接对概率过线打标签；评测和线上推理则共用[空标签兜底](../../scripts/ch10/inference_lib.py#L6)，所有类别都不过线时取最高分标签。两者决策口径并非完全一致，后续可以统一后重新扫描；低分强制分配也不能解释成模型有把握。

**5. ONNX 导出证明了什么？**

模型导出支持动态 batch 和序列长度；在同一批测试输入上检查 logits 容差 `1e-3` 及过线标签一致。当前导出报告（本机归档 `data/ch10/reports/export_report.json`，未随源码发布）是 149 条、0 条不一致。它证明此批输入下转换结果一致，不证明加速倍数、生产吞吐或对所有输入都完全等价。源码：[导出及校验](../../scripts/ch10/export_onnx.py#L46)。

**6. 点踩之后会自动把新答案写回知识库吗？**

不会。点踩只入问题池；批处理产出标准化问题、匹配已有缺口或新建待审项；AI 生成的是草稿；人工审核提交核准答案后才写回。未归并问题不会被旁路分类器提前分类。用户反馈快照只能尽力回捞，因此某条点踩没有快照也是允许的状态。

**7. 写 MySQL 和 Milvus 是一个事务吗？**

不是。先写 MySQL pending，嵌入与 Milvus upsert 后回填完成状态，再更新审核状态。[双写流程](../../app/kb/dualwrite.py#L28)可重跑；[审核接口](../../app/api/review.py#L72)在异常时保持待审并尝试清理本次 pending 数据。不能称为跨存储强事务，仍需处理部分成功、补偿失败以及并发审核等窗口。

**8. 怎么证明“反馈系统让客服更好”？**

现有代码证明问题可追踪、可归并、可审核补库，分类报告证明主题分类的离线效果；还缺少冻结问集上的补库前后对照。可补的实验是：固定知识库版本和缺口问集，人工核准补库后重跑相同问题，同时观察解决率、误答率与已有问题回归，保留新增条目和报告版本。没有这组实验时，不给出提升百分比。
