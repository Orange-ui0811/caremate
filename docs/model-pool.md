# 模型调用池与结果回放

参考 `D:/Orangejd/orange-server/src/main/java/com/orangejd/server/foundation/aitool/` 中的 `AiToolRouter`、`AiToolSlotLeaseService`、`AiResultRecorder`，将全局/单Key容量、错误分类、租约释放和业务结果回放接入CareMate。容量以本项目实测为依据。2026-10-22 经用户授权从指定本机环境文件导入十个同厂商 Key，具体密钥不进入源码和报告。

## 实际接入

- `app/core/model_pool.py`：SQLite WAL短事务原子抢占、FIFO有界等待、前台优先、后台容量限制、失效/冷却Key、TTL过期回收与按持有者释放。同一令牌用于聊天、向量化和重排时共用容量；Gitee两个域名按同一供应商归并。
- `app/core/model_transport.py`：治理实际HTTP请求，兼容LangChain Function Calling、普通响应和SSE；连接按用途/事件循环复用。流式请求从获取响应到读完/关闭一直占用槽位，中途失败不会重新请求并重复输出前缀。
- `app/api/chat.py`：客户端带`request_id`时完成结果落盘。相同用户、相同ID、相同消息和会话才可回放；同ID不同内容返回409，执行中的重复请求也返回409。中断或状态不明的请求禁止自动重做，以免重复执行工具。仅被会话互斥拒绝、尚未执行的请求可以复用该ID再次提交。
- 后台摘要和管理端作业标记为后台优先级；同一会话的并行`/api/chat`请求被拦截，防止图状态交错。不同会话可并行。
- 流式累计Token计数改为任务局部状态，避免复用同一模型实例时不同请求互相污染。

## 默认设置与管理入口

访问 `/model-pool`（管理端导航“模型调用池”）：查看正在执行的调用、等待数、Key指纹、失效/冷却状态、近期attempt与回放结果数量。可保存总并发、单Key并发、后台并发、队列容量、排队时间、单次调用期限、连续无数据超时和最多尝试次数；新调用立即使用新设置。恢复/重置Key会清除失效与冷却标记，停用不会强杀正在执行的调用。

默认：总并发4、单Key并发2、后台最多1、等待队列64、排队最多3秒、单次HTTP调用总预算30秒、连续无数据15秒、最多2次尝试。聊天整轮期限60秒，完成结果默认保留24小时。只有一个Key时实际容量最多2，不会凭空得到4个或80个供应商并发槽。容量配置不是供应商额度承诺，增加同账号的Key也不保证上游额度独立。

聊天、向量化和重排分别保留原模型与接口配置。管理页“添加 Key”支持批量粘贴并选择用途，立即生效，无需重启；首次添加会保留该用途的原环境 Key，之后可停用或移除。同一厂商的十个 Key 可以用于全部三个通道，共享每 Key 并发限制。没有管理配置时仍使用环境变量，聊天的 `MODEL_POOL_CHAT_KEYS` 为空时使用 `CHAT_API_KEY`。删除管理列表最后一个 Key 不会悄悄恢复环境 Key。备用供应商仍需显式配置 `MODEL_POOL_FALLBACK_BASE_URL`、`MODEL_POOL_FALLBACK_API_KEY` 和 `MODEL_POOL_FALLBACK_MODEL`；自定义意图/摘要模型不会被强行切换为默认聊天备用模型。

管理端保存的容量策略优先于 `.env` 中的默认值。模型名、地址、环境 Key、数据库路径和整轮/回放期限修改后需要重启服务；通过管理页新增/移除 Key 不需要重启。`MODEL_POOL_ENABLED=false` 可回到原直连模型入口（使用环境 Key），聊天请求 ID 的防重复执行保护仍保留。日志和管理 API 仅展示指纹。

新增 Key 的接口为 `POST /api/model-pool/keys`，请求包含 `keys` 数组与 `channels` 数组；删除为 `DELETE /api/model-pool/keys/{fingerprint}`。当前演示管理端没有登录系统，因此密钥写入限本机且校验同源请求。密钥以 Fernet 密文保存到 SQLite，主密钥为同目录的 `.sqlite3.key` 文件；备份/迁移需同时保护这两个文件，拥有两者的本机用户仍能解密。两者均忽略入库，接口不提供密钥读回功能。

2026-10-22 本机实测后的在用设置：总活动并发 64、单 Key 64、后台 32、最大等待数 512、排队 30 秒、调用总期限 90 秒、无数据 60 秒、最多尝试 2 次；整轮期限 180 秒。64 是本次无失败短请求批次验证过的活动并发，不能推导出每 Key 永远支持 64，也不能把十 Key 相乘设成 640。相同账户可能共享配额，模型/上下文/时间窗口变化后应重测。代码中的通用初始默认仍适用于未校准的部署。

## 超时与重试语义

401/403使对应Key失效，429遵守Retry-After进入冷却，5xx短暂冷却；在尚未暴露成功响应体前可以换Key有限重试。网络层重试由池统一负责，OpenAI SDK重试关闭，结构化层只对解析失败/缺少tool_calls原样重试一次。排队、尝试和响应读取共用单次HTTP调用预算；异步流有总期限。同步脚本还受底层读取超时约束，最后一次阻塞读取最多可比总预算多一个读取超时；线上客服使用异步路径。

结果回放的是完整客服SSE结果，覆盖工具徽章、正文、引用、动作和会话ID；不会把相同文本但不同请求ID当成可复用答案，也不会把先前生成的回答用于另一用户。接口收到请求ID后先登记再开始生成，完成结果在最终DONE帧之前写入；因此客户端丢失最后一帧仍可以取回完成结果。客户端中断造成不确定状态时应先核查会话/工具记录。供应商已接收但未回执的超时无法保证不计费，回放也不能提供外部副作用的严格exactly-once保证。

## 协调范围和部署边界

运行数据在`data/model_pool.sqlite3`，已被现有gitignore覆盖。同一主机上的API worker和脚本必须指向同一个绝对文件路径，共享全局与Key槽位；SQLite是单写者，进程内先串行化短写事务，进程之间由数据库锁协调。不同机器、不同容器各自的本地文件不能形成集群全局限额；多机部署需要改为共享Redis/MySQL租约实现，不能将此版本称为Redis分布式调用池。不要把SQLite文件放在网络共享目录上模拟多机协调。

重启丢失的模型租约会在期限后回收；过期持有者不能释放新调用的槽。请求ID回放保留期内保留已完成响应及请求摘要哈希，未完成请求不会自动恢复执行。后台摘要在应用关闭时取消并释放槽位。会话互斥目前覆盖聊天入口，动作续跑和其他业务接口仍依赖其原有工具确认/审计语义，不能据此声称整个业务流程已实现端到端exactly-once。

## 容量测试（2026-10-22）

`scripts/benchmark_model_pool.py` 对真实模型递增加压，支持单 Key / 十 Key 直连与生产调用池三种对照。使用短合成问题、128 输出 token 上限、关闭思考、禁用厂商故障转移。每轮保存状态、吞吐、P50/P95、token 与逐请求耗时，不保存凭据或回复正文。遇错误或 P95 超过 45 秒停止升级。它测的是模型请求，不是完整客服人数。

`scripts/benchmark_chat_capacity.py` 则通过真实 `/api/chat` ASGI 路径运行商品知识问题，包含 LangGraph、检索、数据库和模型调用，独立 checkpoint 与调用池数据库。生成专用测试用户，会话结束后软删除；仍保留数据库审计记录。关闭 Langfuse 以免混入业务模型成本看板。ASGI 测试不含真实网络连接、代理和浏览器开销；成功表示 SSE 正常结束，并不自动等于回答质量正确。报告也记录答案长度、引用数量和活动节点。

所有实际测试结果在 `data/verification/pool-*-20261022.json`。直连模式使用同样模型和合成请求；生产适配器使用有限重试，因此对比反映“排队 + 路由 + 重试”整体效果。测试按顺序进行，供应商负载会波动，单次短批次的差值不能作为长期 SLA 或纯路由优化的因果证据。

### 本次结果

汇总与原始报告索引：`data/verification/pool-capacity-summary-20261022.json`。

| 实际场景 | 完成数 | P95 完成耗时 | 成功吞吐 |
| --- | --- | --- | --- |
| 单 Key 直连，64 个短请求同时到达 | 64/64 | 23.84 秒 | 2.455 请求/秒 |
| 十 Key 直连，128 个短请求同时到达 | 98/128，其余 429 | 14.17 秒（仅成功请求） | 4.564 请求/秒 |
| 十 Key 调用池，128 个短请求同时到达，最多 64 个活动调用 | 128/128 | 22.62 秒 | 5.038 请求/秒 |
| 单 Key 直连，16 个真实客服流程同时开始 | 16/16 | 117.48 秒 | 0.136 轮/秒 |
| 十 Key 调用池，16 个真实客服流程同时开始 | 16/16 | 88.83 秒 | 0.180 轮/秒 |
| 十 Key 调用池，32 个真实客服流程同时开始 | 31/32 | 121.39 秒（仅成功轮次） | 0.252 轮/秒 |

单 Key 的 128 并发探测出现 1 次 429，因此在用单 Key 容量取本次验证无失败的 64，并未测出厂商固定硬上限。十 Key 的 128 请求对照中，调用池将成功率从 76.56% 提至 100%，成功吞吐增加约 10.4%，但排队使成功请求 P95 变长。16 人完整流程对照的吞吐增加约 32.2%，P95 降低约 24.4%；4 人时 P95 仅从 48.67 秒变成 47.31 秒，低并发没有明显提速。

完整流程的 16 人批次全部返回引用，但 P95 约 89 秒，仍不能承诺一分钟内完成。32 人批次已经出现模型超时，且 MCP 客户端记录了流关闭/资源断开异常，因此不能作为稳定支持 32 人的证据。本次可确认“16 个同时提问均完成”，不能据此承诺持续在线容量，也不能把 128 个短模型请求解释为 128 个客服用户。回答质量需要独立评估。模型调用池的队列等待平均约零点几秒，此后优化需进一步定位每轮多次串行模型调用、检索、工具发现/连接与生成的耗时。

当前参数含义：64 的活动并发以无错误探测结果为依据；后台 32 为前台保留容量；512 是等待队列的保护边界，不代表 512 人容量；30 秒排队用于吸收短批次突发；90 秒调用总期限、60 秒无数据期限适应实测慢调用；2 次尝试避免重试放大流量；180 秒整轮期限覆盖多步流程。超时和重试次数不是供应商并发额度，不应一律设到表单允许的最大值。
